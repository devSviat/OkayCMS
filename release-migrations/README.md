# release-migrations/

Core-специфічні DB-міграції форку. Кожен файл — `{fork-version}_{опис}.up.sql`,
ідемпотентний (`CREATE TABLE IF NOT EXISTS`, перевірка через
`INFORMATION_SCHEMA` перед `ALTER`).

## Головне правило: файли звідси НЕ видаляють

Реліз-пайплайн (`ok release:build-package`, `.github/workflows/release.yml`)
кладе в `migrations/` пакета релізу **всі** файли з цього дерева (рекурсивно),
а не лише нові з часу попереднього релізу.

Так треба, бо оновлювач качає **лише останній** реліз. Якщо інсталяція стоїть
на 1.0.1, а вийшла 1.3.1 — вона стрибає одразу на 1.3.1, і міграції релізів
1.1.x/1.2.x мусять бути в цьому ж пакеті. Інакше вони не потраплять нікуди
й будуть втрачені назавжди.

Повторного застосування боятись не треба: `CoreMigrator` веде трекер
`ok_core_migrations` за **іменем файлу** й пропускає вже застосовані, а
порядок визначає натуральним сортуванням імен (`1.2.0_x` перед `1.11.0_y`).

## Вимоги до імен

Ім'я файлу — ключ ідемпотентності в трекері, тому воно мусить бути
унікальним у межах усього дерева. Збірка пакета падає з явною помилкою,
якщо знайде два файли з однаковим `basename` у різних підкаталогах.
Розкладати історію по підкаталогах (напр. за мажорною версією) можна —
обхід рекурсивний.

## Діалект SQL (`CoreMigrator::splitSqlFile()`)

Парсер простий, це не повний SQL-парсер:

- Коментар — лише `--` з нульової позиції рядка (відступ перед `--` НЕ
  зрізається); `#` і `/* */` не розпізнаються — не використовуйте їх.
- Стейтмент завершується будь-яким рядком, чий обрізаний хвіст — `;`,
  без урахування лапок — навіть усередині рядкового літерала. Тому
  багатостейтментні прийоми на кшталт `SET @s = ...; PREPARE ...` в межах
  однієї логічної операції мають тримати кожен `;` рівно на кінці рядка
  справжнього стейтменту.
- Таблиці пишуться як `__name` (два підкреслення) — префікс (`ok_` тощо)
  підставляється під час `apply()`, той самий синтаксис, що і в решті бази.

Формат і механізм застосування на боці CMS — `docs/updates.md` і
`docs/superpowers/specs/2026-08-30-core-self-updater-design.md`, §7.
