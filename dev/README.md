# Docker-оточення OkayCMS

Оточення складається з Nginx, php-fpm (`php85`), MariaDB, окремого контейнера
`scheduler` (виконує `./ok scheduler:run` за розкладом) та, в dev-режимі,
Mailpit для перехоплення пошти. Базова конфігурація (`docker-compose.yml`)
спільна для dev і prod; dev-специфіка (бінд-маунти коду, опубліковані порти,
Xdebug, сідовий дамп бази, Mailpit) винесена в `docker-compose.override.yml`,
який Compose підвантажує автоматично.

## Швидкий старт

Усі команди нижче виконуються з теки `dev/` — одним блоком, без переходів
між директоріями посередині:

```bash
cd dev
cp .env-example .env

# APP_UID/APP_GID мають збігатися з вашим хостовим користувачем, інакше файли,
# які контейнер пише в бінд-маунтнуту теку проєкту, вийдуть недоступними для
# запису з хоста.
sed -i "s/^APP_UID=.*/APP_UID=$(id -u)/" .env
sed -i "s/^APP_GID=.*/APP_GID=$(id -g)/" .env

docker compose up -d
./bin/smoke.sh
```

Скрипт можна запускати з будь-якої теки — він сам переходить куди треба
(`dev/bin/smoke.sh` з кореня репозиторію працює так само). Він дочекається, поки всі
контейнери зі здоров'я-чеком стануть `healthy`, дочекається завершення
одноразового `db-init`, і лише тоді прожене перевірки: PHP-конфігурацію та
розширення, що база на named volume, мережеву ізоляцію mariadb, що scheduler
живий, що логи nginx йдуть у `docker compose logs`, і що обидва поштові шляхи
долітають до Mailpit. Якщо на машині одночасно піднято кілька копій цього
проєкту — задайте кожній свій `APP_NAME` (з нього береться ім'я compose-проєкту).
Мережі Compose іменує сам, за проєктом: `<APP_NAME>_frontend` і `<APP_NAME>_backend`.

Для чужого зручного доступу по http замість `http://localhost:80`,
`http://localhost:81`... додайте хости в `/etc/hosts` на `127.0.0.1` і
підніміть один зворотний проксі на всі проєкти:

```bash
docker run -d -p 80:80 -v /var/run/docker.sock:/tmp/docker.sock:ro \
  --net "$(docker compose ps --format '{{.Name}}' nginx | head -1 | sed 's/-nginx-1$//')_frontend" \
  nginxproxy/nginx-proxy
```

(nginx сам сидить лише у `frontend` — `backend` є `internal: true`
і без маршруту на хост, тож проксі туди підключати сенсу немає. Мережі з'являються
лише після першого `docker compose up`; перевірити фактичні назви — `docker network
ls`.)

Після цього сайт буде доступний по http на хост, вказаний у `.env` як
`VIRTUAL_HOST`, на 80-й порт — незалежно від того, який `HTTP_PORT` вказаний
для самого проєкту.

## УВАГА: `docker compose down -v` тепер знищує базу даних

База MariaDB тепер живе на named volume (`db_data`), а не в бінд-маунтнутій
`dev/mysql/DB_data` — цієї директорії більше не існує. Це навпаки старій
звичці: раніше `down -v` не чіпав дані бази, бо вони лежали поза Docker-
керованими volume. Тепер `-v` видаляє volume разом з даними без попередження
й без можливості відновлення. Просте `docker compose down` (без `-v`) дані не
чіпає — саме його і варто використовувати за замовчуванням. `down -v`
запускайте свідомо, лише коли дійсно потрібно почати з чистої бази (при
цьому `db-init` при наступному `up -d` знову накотить дефолтний дамп
`1DB_changes/okay_clean.sql` і пересоздасть менеджера `admin`).

## Xdebug

Режим Xdebug перемикається змінною `XDEBUG_MODE` в `.env` (`off` або
`debug`) і застосовується одразу на `docker compose up -d` — образ
пересобирати не потрібно, оскільки Xdebug 3 читає цю змінну середовища й вона
має пріоритет над ini-файлом:

```bash
sed -i "s/^XDEBUG_MODE=.*/XDEBUG_MODE=debug/" .env
docker compose up -d
```

Щоб налаштувати Xdebug для роботи з PHPStorm треба зробити наступне:

1. Ідемо в Settings > PHP > Servers і додаємо сервер.
Host та port указуємо як в файлі .env (VIRTUAL_HOST, HTTP_PORT)
2. Також тут налаштовуємо Path mapping (корень сайта на хостовій машині указуємо як /var/www/html на сервері)
3. В Settings > PHP > Debug > XDebug додаємо порт 9001
4. Ідемо в Run > Edit configurations та створюємо конфігурацію на основі `PHP Remote Debug`
В полі Server указуємо сервер створений вище, в IDE key вписуємо PHPSTORM.
Назву рекомендую вказувати як host:port

## Пошта

Усі листи з локального оточення перехоплює Mailpit — жоден лист нікуди
далі не піде. Веб-інтерфейс: `http://127.0.0.1:8025` (порт береться зі
змінної `MAILPIT_PORT` у `.env`).

Перехоплюються обидва транспорти, якими користується OkayCMS:

- **`mail()`** — `sendmail_path` в dev-образі вказує на `msmtp`, який
  безумовно шле все на `mailpit:1025` (див. `dev/config/php/custom.d/dev.ini`).
- **SMTP** (`Okay/Core/Notify.php`, коли в адмінці увімкнено `use_smtp`) —
  на кожному `docker compose up` одноразовий контейнер `db-init` перезаписує
  налаштування `smtp_server`/`smtp_port` в `ok_settings` на `mailpit`/`1025`,
  так що навіть якщо хтось увімкне SMTP-розсилку в адмінці, лист все одно
  піде в Mailpit, а не назовні.

Щоб db-init не чіпав ці налаштування (наприклад, якщо свідомо тестуєте
реальний SMTP-сервер), виставте в `.env`:

```
DB_INIT_SMTP=0
```

`TEST_INTERNAL_EMAIL` з `.env` як і раніше підтримується, але Mailpit дає
сильнішу гарантію — жоден лист не покидає машину — тож для локальної
розробки окремо його налаштовувати вже не обов'язково.

## Логи

Логи всіх сервісів (включно з access/error-логами nginx) тепер ідуть у
stdout/stderr контейнера, а не у файли під `dev/logs` — цієї директорії
більше немає. Дивитись:

```bash
docker compose logs nginx
docker compose logs php85
docker compose logs scheduler
docker compose logs -f      # усі сервіси одразу, у реальному часі
```

## Порти

Опубліковані порти nginx і Mailpit (`HTTP_PORT`, `MAILPIT_PORT`) за
замовчуванням прив'язані лише до `127.0.0.1` — з інших машин у мережі
оточення недоступне. Щоб свідомо відкрити їх назовні (наприклад, тестувати з
телефону в тій самій мережі), виставте в `.env`:

```
BIND_IP=0.0.0.0
```

і перезапустіть `docker compose up -d` — рекреейт торкнеться лише сервісів,
які публікують порти (`nginx`, `mailpit`).

`MYSQL_PORT` працює так само, як порти nginx і Mailpit вище — база доступна з
хоста на `${BIND_IP:-127.0.0.1}:${MYSQL_PORT}`, тож DBeaver, вбудований
Database tool у PHPStorm чи звичайний `mariadb`-клієнт підключаються напряму:

```bash
mariadb -h 127.0.0.1 -P "$MYSQL_PORT" -uroot -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE"
```

Це навмисний виняток лише для розробки. У базовому файлі (`docker-compose.yml`)
`mariadb` сидить лише в мережі `backend`, яка `internal: true` (без маршруту з
контейнера назовні) — і саме так лишається в проді (`docker-compose.prod.yml`
нічого тут не змінює, порт лишається неопублікованим). Docker не вміє
публікувати порт контейнера, чия єдина мережа internal — NAT-правило просто не
створюється незалежно від `BIND_IP`. Тому `docker-compose.override.yml`
(діє лише в dev) додатково підключає `mariadb` ще й до мережі `frontend`, яка
має маршрут на хост — це і відкриває опублікований порт. Прод-ізоляція від
цього не страждає: `docker-compose.prod.yml` override.yml не використовує.

## Scheduler

Окремий контейнер `scheduler` тепер справді працює: всередині — `supercronic`
під `tini`, який щохвилини виконує `php ok scheduler:run`. Це не означає, що
кожне завдання планувальника запускається щохвилини — `Scheduler::run()` сам
вирішує для кожного зареєстрованого завдання, чи воно дійсно due (за власним
cron-правилом задачі, `Okay\Core\Scheduler\Task::isDue()`), тож щохвилинний
тик — це дешева перевірка "чи щось назріло", а не безумовний запуск усіх
завдань. Перевірити, що воркер живий і справді щось запускає:

```bash
docker compose logs scheduler
docker compose exec scheduler pgrep -fa supercronic
```

## Ресайз зображень

Коли на локальний сервер береться БД з production сайта, завжди є проблема з оригіналами зображень товарів, категорій тощо.
Тому можна вказати в .env файлі змінну PRODUCTION_DOMAIN, де буде вказаний домен, з якого бралась база,
і нарізки зображень братимуться з того домена по http. Важливо, це працюватиме лише для зображень, розмір ресайзу
яких співпадає з production сервером.
На локальний сервер в директорію originals зображення не додаються, вони збережуться лише в resized директорію.

## Продакшн

Продакшн-конфігурація — опційний оверлей `docker-compose.prod.yml`, який
ніколи не підвантажується автоматично; його треба явно додати поверх базового
файлу. Він не публікує жодного порту на жодному сервісі і монтує
`config/config.local.prod.php` (готується окремо, див. нижче) в контейнери
`php85`/`scheduler` в режимі read-only. Підтримуються дві форми деплою:

**1. За PaaS/reverse proxy, який сам приєднується до контейнера** — Dokploy,
Coolify, або просто власний Traefik. Жодних опублікованих портів не потрібно:
проксі підключається до контейнера `nginx` напряму по мережі `frontend`:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
```

**2. Standalone, без reverse proxy перед оточенням** — додається третій файл,
який єдине що робить — публікує порт nginx назовні (порядок файлів важливий:
`docker-compose.prod.yml` має йти перед `docker-compose.standalone.yml`, щоб
`ports:` з останнього лягли поверх того самого сервіса `nginx`):

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml \
               -f docker-compose.standalone.yml up -d
```

Не додавайте `docker-compose.standalone.yml` поверх такого деплою — проксі
і так ходить до nginx по мережі `frontend`, а зайва публікація порту тільки
розширює поверхню атаки без жодної користі.

У standalone-формі `BIND_IP` має дефолт `0.0.0.0`, а не `127.0.0.1` як у dev:
цей файл існує рівно для хоста, який сам приймає трафік ззовні, і з петльовим
інтерфейсом сайт був би недоступний саме там, де має працювати.

**Але дефолт спрацьовує лише тоді, коли змінна взагалі не задана.** Файл
`dev/.env` (той, що ви робите з `.env-example` для розробки) виставляє
`BIND_IP=127.0.0.1` явно — і якщо він лежить поруч на прод-хості, standalone
підхопить саме його, а сайт мовчки слухатиме тільки петльовий інтерфейс.
Тому на прод-хості або не тримайте dev-івський `.env`, або виставте значення
свідомо:

```bash
BIND_IP=0.0.0.0 docker compose -f docker-compose.yml -f docker-compose.prod.yml \
                               -f docker-compose.standalone.yml up -d
```

Перевірити, що вийшло насправді:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml \
               -f docker-compose.standalone.yml config | grep -A2 published
```

Якщо треба вужче — задайте конкретний інтерфейс, наприклад `BIND_IP=10.0.0.5`.
Firewall на хості лишається вашою відповідальністю.

Перед першим запуском в обох формах:

- Підготувати рантайм-конфіг застосунку: скопіювати
  `config/config.local.prod-example.php` в `config/config.local.prod.php`,
  прописати реальний `db_password` (для окремого, непривілейованого MySQL-
  користувача — на відміну від dev, де застосунок ходить під root),
  виставити `chmod 600` і власника — деплой-юзера.
- Задати паролі бази у змінних оточення: `MYSQL_ROOT_PASSWORD`, `MYSQL_PASSWORD`,
  `MYSQL_USER`, `MYSQL_DATABASE`. На standalone-хості це `.env` поруч із
  compose-файлами, на PaaS (Dokploy, Coolify тощо) — його панель змінних оточення. Файл `.env` теж має
  бути `chmod 600` і належати деплой-юзеру.

  **Що саме захищає паролі, без прикрас.** Межа — це права доступу на хості:
  на `.env` і на `config/config.local.prod.php`. Змінні оточення видно у виводі
  `docker inspect`, тож не вставляйте його в тікети й не збирайте моніторингом
  без фільтрації.

  Тут раніше були Docker secrets із конвенцією `*_FILE`. Їх прибрано свідомо:
  вони прибирали пароль БД з `docker inspect`, але не давали захисту від того,
  хто вже має доступ до Docker (`docker exec … cat /run/secrets/…` читається так
  само, а група `docker` фактично дорівнює root), і головне — пароль, яким у
  базу ходить сам застосунок, однаково лежить відкритим текстом у
  `config.local.prod.php`, бо OkayCMS читає його звідти, а не з оточення.
  Механізм закривав одну дірку з двох, коштуючи окремих файлів секретів і
  вимоги виставляти фіктивну змінну, яка нікуди не йде.

- **Ініціалізувати базу даних.** У проді немає ані сервісу `db-init`, ані
  монтування сід-дампа — і це навмисно: автоматично заливати дамп у продакшн
  означало б ризик затерти живі дані при кожному `up`. База піднімається
  порожньою, схему створює оператор один раз. Два шляхи, залежно від ситуації.

  *Новий магазин з нуля* — залити чистий дамп із репозиторію:

  ```bash
  docker compose -f docker-compose.yml -f docker-compose.prod.yml \
    exec -T php85 php ok database:deploy
  ```

  Команда бере `1DB_changes/okay_clean.sql` (шлях перевизначається через
  `--file_path`). Далі обов'язково задати пароль менеджера — дамп містить
  дефолтний `admin`, і лишати його в проді не можна:

  ```bash
  docker compose -f docker-compose.yml -f docker-compose.prod.yml \
    exec -T mariadb sh -c 'mariadb -uroot -p"$(cat /run/secrets/mysql_root_password)" \
    "$MYSQL_DATABASE" -e "UPDATE ok_managers SET password = ... WHERE login = \"admin\";"'
  ```

  Хеш генерується в форматі APR1-MD5 (`Okay\Core\Security\PasswordHasher`);
  найпростіше — змінити пароль через адмінку одразу після першого входу.

  *Перенесення наявного магазину* — відновити свій бекап замість дампа:

  ```bash
  docker compose -f docker-compose.yml -f docker-compose.prod.yml \
    exec -T mariadb sh -c 'mariadb -uroot -p"$(cat /run/secrets/mysql_root_password)" \
    "$MYSQL_DATABASE"' < backup.sql
  ```

  Після оновлення коду на вже наповненій базі застосовуються міграції модулів —
  див. `docs/modules/table_migrate.md`; `database:deploy` для цього не
  призначений, він заливає саме чисту базу.

- Для реального деплою (не першого пробного піднімання) явно виставити
  `OKAY_VERSION` на конкретний незмінний тег образу. За замовчуванням
  використовується `latest` — свідомо, щоб перший `up` у щойно створеному
  оточенні PaaS не впав ще до того, як хтось встиг відкрити його UI і щось
  налаштувати, — але прод-оточення, яке лишає `OKAY_VERSION=latest` назавжди,
  не має запису, яка саме версія коду виконується, і не має до чого
  відкотитись при невдалому пуші.

## Обмеження

Це не готовий до бойового трафіку продакшн з коробки — воно навмисно не
намагається бути таким:

- **Немає TLS і немає бекапів.** Перед оточенням мається на увазі зворотний
  проксі (Dokploy/Traefik або власний), який термінує TLS. Резервне
  копіювання бази (`db_data`) і `files/` — окрема відповідальність, тут її
  немає взагалі.
- **Лише один вузол (single-node).** `Okay\Core\Config` обчислює
  `$salt` через `stat()` файлу `config/config.php` — беручи його device id,
  inode і mtime (`Okay/Core/Config.php:147`: `md5(md5_file(...).$s['dev'].$s['ino'].$s['uid'].$s['mtime'])`).
  `AdminRecoveryToken` підписує токени відновлення пароля адміністратора
  саме цією сіллю. Тому кожен ребілд образу — це нові inode/mtime файлу
  всередині нового шару, тобто нова сіль, і всі видані раніше токени
  відновлення пароля миттю стають недійсними; а якщо запустити дві репліки
  одночасно (два контейнери з тим самим кодом, але різними inode — це
  практично гарантовано навіть у межах одного хоста), вони порахують різну
  сіль і не зможуть звірити токен, виданий одна одною. Горизонтальне
  масштабування цього оточення в поточному вигляді не підтримується.
- **Docker secrets захищають лише облікові дані самого контейнера MariaDB**
  (щоб `MYSQL_ROOT_PASSWORD`/`MYSQL_PASSWORD` не світились у
  `docker inspect`) — і більше нічого. Пароль застосунку до бази OkayCMS
  бере не з середовища, а з `config/config.local.php`, тож ані ця
  Docker-secrets-обв'язка, ані будь-яка інша змінна середовища його не
  прикриває. Межа захисту для цього файлу — `chmod 600`, власник
  деплой-юзер, монтування в контейнер тільки для читання (це вже зроблено в
  `docker-compose.prod.yml`) і виключення з build-контексту
  (кореневий `.dockerignore`, перевіряється `dev/bin/smoke-prod.sh`).
- **Редагування теми чи `robots.txt` через адмінку в продакшні не спрацьовує
  взагалі — файл не пишеться жодного разу, не те що "до наступного деплою".**
  `design/*/css/theme-settings.css` і `robots.txt` закомічені в git,
  потрапляють в образ через `COPY .` на етапі білду і належать `root`
  (їх немає в `chown`-списку `dev/docker/Dockerfile`), а php-fpm у `prod`
  виконується від `www-data`. Жодного з цих шляхів немає серед volume в
  `docker-compose.prod.yml`, тож права не змінюються і після старту
  контейнера. Перевірено напряму в зібраному `prod`-образі (`is_writable()`
  повертає `false` на обидва файли, `file_put_contents()` — `Permission
  denied`), і поведінка в адмінці для двох цих полів **різна**:
  - `robots.txt` (`backend/Controllers/RobotsAdmin.php`) сам перевіряє
    `is_writable()` перед записом і, якщо `false`, показує
    `message_error = 'write_error'` — адмін одразу бачить помилку, запис
    навіть не виконується.
  - Кольори теми (Налаштування → Тема) записуються через
    `Okay\Core\TemplateConfig\CssConfig::updateCssVariables()`, яка викликає
    `file_put_contents()` без жодної перевірки. Запис мовчки провалюється:
    PHP-попередження `Failed to open stream: Permission denied` летить лише
    в лог (`display_errors = Off` у `prod.ini`, тож у браузер нічого не
    йде; `log_errors = On`, тож рядок є в `docker compose logs php85`), а
    `SettingsThemeAdmin::fetch()` однаково показує `message_success =
    'saved'` — адмінка каже "збережено", хоча файл не змінився. Шукати таку
    поведінку без цього абзацу — типове полювання на "баг", який насправді
    задуманий: правки теми й `robots.txt` мають потрапляти в репозиторій, а
    не робитись через адмінку прод-сайту (`design/*/lang/local.*.php` —
    мовні перевизначення — з тієї ж причини в `.gitignore` і теж не мають
    редагуватись наживо в проді). Із завантаженими зображеннями товарів
    інакше — `files/` це named volume, і він переживає редеплой.
