# Оновлення: посилення безпеки

Цей документ описує все, що змінюється у поведінці після security-ітерації, і що саме треба
зробити авторам тем і модулів.

**Кому читати:** усім, хто підтримує кастомну тему, кастомний модуль або власні AJAX-виклики до
вітрини чи адмінки. Якщо ви працюєте лише через стандартну тему й інтерфейс адмінки, дій від вас
не потрібно — крім одноразового розлогіну користувачів.

**Схема бази не змінюється.** Оновлення відбувається розгортанням коду, без міграцій.

Повний перелік закритих дефектів — у
[`docs/superpowers/specs/2026-07-26-security-hardening-design.md`](superpowers/specs/2026-07-26-security-hardening-design.md).

## 1. Усі сесії розлогінюються один раз

Ім'я сесії більше не обчислюється як `md5($_SERVER['HTTP_USER_AGENT'])`. Вітрина отримала
`okay_sid`, адмін-панель — `okay_admin_sid`.

Раніше покупець і менеджер жили в одній куці, а ім'я залежало від заголовка запиту.

**Наслідок:** на деплої всі активні покупці й менеджери розлогінюються. Одноразово.

**Що робити:** нічого. Ідентифікатор сесії тепер також оновлюється при кожній зміні рівня
привілеїв — вхід, реєстрація, вихід, скидання пароля.

---

## 2. Мутації вітрини вимагають POST і CSRF-токен

Найширша зміна. Раніше `/cart/{id}` і `/cart/remove/{id}` були звичайними GET-адресами: будь-яка
стороння сторінка могла наповнити або очистити кошик відвідувача тегом `<img>`.

**Захищені ендпоінти:**

| Адреса | Було | Стало |
| ------ | ---- | ----- |
| `/cart/{variantId}` | GET | POST + токен |
| `/cart/remove/{variantId}` | GET | POST + токен |
| `/ajax/cart_ajax.php` | GET | POST + токен |
| `/ajax/wishlist.php` | GET | POST + токен |
| `/ajax/comparison.php` | GET | POST + токен |
| `/ajax/subscribe` | POST | POST + токен |
| форма зворотного зв'язку | POST | POST + токен |
| форма коментаря | POST | POST + токен |

**Коди відмови:** GET на мутацію → `405`, відсутній або невірний токен → `403`.

**Що робити у формах теми:**

```smarty
<input type="hidden" name="customer_csrf_token" value="{$customer_csrf_token|escape}">
```

Змінна `customer_csrf_token` доступна в будь-якому шаблоні вітрини — її призначає
`AbstractController`.

**Що робити в AJAX:** токен дублюється в куку `okay_csrf`, яка навмисно **не** `HttpOnly`, щоб
скрипти могли її прочитати:

```javascript
function okayCsrfToken() {
    var match = document.cookie.match(/(?:^|;\s*)okay_csrf=([0-9a-f]{64})/);
    return match ? match[1] : "";
}
```

Далі додайте `customer_csrf_token: okayCsrfToken()` у дані кожного мутуючого запиту і переконайтесь,
що він іде методом POST.

**Читання параметрів:** `wishlist`, `comparison` і `cartAjax` раніше брали параметри з `$_GET`.
Тепер вони читають їх з `$_POST`.

## 3. Паролі перехешовуються прозоро

Паролі менеджерів були APR1-MD5, покупців — `md5($salt . $pass . md5($pass))`. Обидва замінені на
`password_hash()` з Argon2id (bcrypt як запасний варіант).

**Що робити:** нічого. Старі хеші продовжують працювати й замінюються на новий формат при
наступному успішному вході. Примусового скидання паролів не потрібно.

Argon2id-хеш займає 97 символів і вміщається в наявну колонку `varchar(255)`.

## 4. Посилання відновлення пароля більше не авторизує

Раніше перехід за посиланням з листа одразу встановлював `$_SESSION['user_id']` — тобто саме
посилання було сесією. Тепер воно лише підтверджує токен і відкриває форму нового пароля; вхід
відбувається після фактичної зміни.

У базі зберігається лише digest токена, не сам токен. Відповідь на запит відновлення однакова
незалежно від того, чи існує акаунт.

**Що робити темам, які перевизначають `password_remind.tpl`:** додати стан скидання з полями
`new_password`, `new_password_check`, `reset_password` і `customer_csrf_token`.

**Нові мовні ключі** (`design/okay_shop/lang/{ru,en,ua}.php`):

- `password_remind_letter_sent_generic`
- `password_remind_expired`
- `password_remind_password_empty`
- `password_remind_password_wrong`
- `password_remind_new_password`
- `password_remind_save`

Ключ `password_remind_user_not_found` більше не використовується — він був оракулом наявності
акаунта.

## 5. Адмінський CSRF-токен більше не є ідентифікатором сесії

Поле `session_id` у формах адмінки лишилось із тією самою назвою, і шаблони так само друкують
`{$smarty.session.id}` — змінилося лише **значення**: там тепер випадковий токен, а не
ідентифікатор сесії, який раніше потрапляв у HTML кожної сторінки.

Перевірка перенесена з кінця `backend/index.php` (де вона виконувалась уже **після** контролера і
нічого не захищала) на позицію перед диспетчем. Відмова — `403`.

**Що робити:** нічого, якщо ваші форми вже містять `session_id`. Кастомні AJAX-виклики до адмінки
мають надсилати це поле.

## 6. Файловий менеджер

- **Усі п'ять точок входу** (`dialog.php`, `upload.php`, `execute.php`, `ajax_calls.php`,
  `force_download.php`) тепер вимагають авторизованого менеджера. Раніше чотири з них перевіряли
  лише прапорець `$_SESSION['RF']['verify']`.
- **Завантаження за URL видалено.** Опція `url_upload` вимкнена, а серверний код, що робив `curl`
  на довільну адресу, прибраний — це був SSRF-примітив. Файли треба завантажувати з диска.
- **SVG санітайзуються.** Завантажений SVG переписується за білим списком елементів і атрибутів.
  Скрипти, обробники подій `on*`, `foreignObject` і схеми на кшталт `javascript:` видаляються.
- **Traversal відхиляється** на вході: шлях із запиту з `..`, абсолютний, зі схемою або з
  NUL-байтом дає `400`.

**Що робити:** нічого. Але врахуйте, що анімація та інтерактив у завантажених SVG не переживуть
санітизацію, а елемент `<a>` не входить у білий список — SVG із посиланнями втратить цей вузол
разом із вмістом.

## 7. Завантаження з `backend/files/`

Раніше фільтрувалося лише ім'я файлу; `folder` і `ext` бралися з GET як є. Тепер дозволений набір
folder + file + extension заданий явно, і кожен файл прив'язаний до конкретного права менеджера.

**Наслідок:** менеджер без права `export` більше не завантажить `export.csv`, навіть маючи пряме
посилання. Це стосується експорту товарів, замовлень, користувачів, підписників, статистики,
файлів імпорту та водяного знака.

**Що робити:** нічого, якщо права менеджерів роздані відповідно до їхніх обов'язків.

---

## 8. Cookie отримали `HttpOnly`

Усі куки (`shopping_cart`, `comparison`, `wishlist`, `browsed_products`, `admin_login`,
`userReferer`, `last_position`) тепер мають `HttpOnly`, `SameSite=Lax` і `secure` на HTTPS.

**Що робити:** якщо ваш JavaScript читав ці куки напряму — він більше не зможе. Передавайте
потрібні дані через `data-`атрибути, відрендерені на сервері.

Виняток — `okay_csrf`, який лишається читабельним для скриптів за призначенням.

---

## 9. Заголовки відповіді

`X-Powered-CMS` більше не містить версію. Додані `X-Frame-Options: SAMEORIGIN`,
`X-Content-Type-Options: nosniff` і `Referrer-Policy: strict-origin-when-cross-origin`.

**Що робити:** якщо ви вбудовуєте вітрину в `<iframe>` на іншому домені — це перестане працювати.
Якщо ви парсили версію з банера — теж.

**Рекомендація для production:** вимкніть `expose_php` у `php.ini`, інакше відповіді й далі
нестимуть `X-Powered-By` із версією PHP.

---

## 10. Відкриті редиректи

`prg_seo_hide`, а також цілі, взяті з `HTTP_REFERER` і `REQUEST_URI`, тепер перевіряються на
приналежність до поточного origin. Перехід на чужий домен не виконується — замість нього
відбувається повернення на корінь сайту.

---

## 11. reCAPTCHA більше не пропускає при помилковому ключі

Раніше відповідь `invalid-input-secret` трактувалась як успішна перевірка — одна помилка в ключі
беззвучно вимикала капчу на всьому сайті. Тепер це відмова із записом у лог.

**Що робити:** перевірте, що ключі капчі коректні. Якщо вони були невірні, капча раніше не
працювала, а тепер почне відхиляти форми.

---

## 12. Адмінські редактори теми більше не приймають шляхи

Значення з запиту склеювались з каталогом теми без жодного відсіву. Фільтром слугував
`trim($name, '.')`, який знімає лише крайні крапки, тому `a/../../..` проходив як є.

**Що було можливо** для менеджера з правом на відповідний розділ:

| Точка | Наслідок |
| ----- | -------- |
| `ImagesAdmin`, поле `delete_image` | `unlink()` будь-якого файлу на диску — обмеження за розширенням не було взагалі |
| `ImagesAdmin`, завантаження | запис файлу з дозволеним розширенням поза каталогом теми |
| `ImagesAdmin`, `old_name`/`new_name` | `rename()` за межами теми |
| `ThemeAdmin`, `theme` + `delete_theme` | **рекурсивне** видалення довільного каталогу (`../..`) |
| `TemplatesAdmin` / `ScriptsAdmin`, `file` | читання будь-якого `.tpl` / `.js` з диска |

Тепер усі ці значення проходять через `Okay\Core\Security\SafeFileName`: `basename()` для імен
файлів і `themeName()` для імен тем. Порожній результат означає відмову — дія пропускається.
Порожнє ім'я теми більше не доходить до `delete_theme` (раніше воно дало б `dirDelete('design/')`,
тобто знесло б усі теми).

**Що робити:** нічого, якщо ви працювали через інтерфейс. Кастомні скрипти, які слали в ці поля
шляхи з підкаталогами, перестануть працювати.

## 13. AutoDeploy: командний рядок і ключ збірки

- **Ін'єкція команд.** Канал збірки зберігався в налаштуваннях без перевірки й звідти потрапляв у
  `exec()` усередині подвійних лапок — одна лапка у значенні дописувала довільну команду. Тепер
  `saveChannel()` приймає лише `dev` і `production`, а всі аргументи проходять через
  `escapeshellarg()`.
- **Ключ збірки** порівнювався нестрогим `!=`, який два «числових» рядки виду `0e123…` вважає
  рівними, і не був сталим за часом. Замінено на `hash_equals()`. Невірний ключ більше не
  друкується назад у статус деплою.

---

## 14. Перевірка версії в адмінці

`backend/Controllers/IndexAdmin.php` ходив на `okay-cms.com` з вимкненою перевіркою сертифіката, а
відповідь осідає в сесії й рендериться в адмінці. `CURLOPT_SSL_VERIFYPEER` і
`CURLOPT_SSL_VERIFYHOST` увімкнено.

Налаштування `disable_validate_smtp_certificate` у `Okay\Core\Notify` лишається як є — це свідомий
перемикач адміністратора, а не дефект.

## Залежності

Оновлення й заміни бібліотек, які прийшли з підтримкою PHP 8.5, заодно закрили те, що форк
успадкував. `composer audit` на локі до форку — **11 попереджень у 4 пакетах**; сьогодні — **2 в
одному**.

| Пакет | Було | Стало | Попереджень тоді |
| ----- | ---- | ----- | ---------------- |
| `smarty/smarty` | 3.1.40 | 4.5.6 | 6 (5 високих) |
| `symfony/process` | 5.3.7 | 5.4.47 | 2 (1 висока) |
| `phpunit/phpunit` | 9.5.10 | 9.6.34 | 1 висока, `require-dev` |
| `maximebf/debugbar` | 1.17.2 | 1.17.2 | 2 середні, `require-dev` — лишились |

Найважливіші — у Smarty, бо це рушій шаблонів, який виконується на кожному запиті: інʼєкція PHP-коду
через `extends`-тег (CVE-2024-35226) і через назву блоку або файлу (CVE-2022-29221), вихід із
пісочниці через математичну функцію (CVE-2021-29454), доступ до обмеженого PHP-коду через динамічний
статичний виклик (CVE-2021-21408), XSS в екрануванні JavaScript (CVE-2023-28447) та інʼєкція в
`smarty_function_mailto` (CVE-2018-25047).

Обидва попередження `symfony/process` стосуються лише Windows — перехоплення виконання команди
(CVE-2024-51736) і руйнівні файлові операції під MSYS2/Git Bash (CVE-2026-24739).

**Що лишилось:** два попередження в `maximebf/debugbar` — це застарілий jQuery у його бандлі
(CVE-2019-11358, CVE-2020-11022). Пакет у `require-dev` і на production не потрапляє, тому лишений
свідомо.

Окремо: `openai-php/client`, який замінив `orhanerday/open-ai`, привів із собою Guzzle, і той приніс
власні 9 попереджень — розкриття кук через IP-адресу в домені (CVE-2026-59883), беззвучне зниження
HTTPS-проксі до відкритого тексту (CVE-2026-55568) і заголовки `Proxy-Authorization`, що доходять до
origin-сервера. Закриті оновленням у межах наявного обмеження `^7.11`.

**Як перевірити самому:** `composer audit`. Для стану до форку — `composer audit --locked` над
`composer.lock` із коміту `09820e3`.

## Відомі відкриті дефекти

Ці не закриті **свідомо** — відповідні модулі не використовуються. Якщо ви їх вмикаєте, спершу
виправте.

### WayForPay

`Okay/Modules/OkayCMS/WayForPay/Controllers/CallbackController.php`, метод `payOrder()`:

- **Обхід підпису.** Умова `!empty($data->merchantSignature) && $data->merchantSignature != $sign`:
  якщо підпис **не надіслати взагалі**, перевірка пропускається — неавтентифікований POST із
  правильним id замовлення і сумою позначає його оплаченим.
- **`TypeError` на легітимному колбеку.** `array_key_exists($dataKey, $data)` над `stdClass` — у
  PHP 8 це фатальна помилка, тобто правильно підписаний колбек падає ще до порівняння підписів.

Ці два дефекти взаємно маскуються: через `TypeError` виконання не доходить до перевірки підпису,
тому обхід стає досяжним лише після виправлення першого. Виправляти їх треба разом.

### RozetkaPay

`Okay/Modules/OkayCMS/RozetkaPay/Controllers/CallbackController.php`

**Лишається відкритим:** підпис колбека не перевіряється. RozetkaPay надсилає заголовок
`X-ROZETKAPAY-SIGNATURE`, але точна схема його обчислення у публічній документації не наведена,
тому перевірку не додано — помилкова реалізація відхиляла б легітимні платежі. Єдина перепона —
збіг `$data->id` зі збереженим id платежу. Для повноцінного захисту потрібна верифікація підпису
за специфікацією від провайдера.

**Виправлено в цій ітерації:**

- Перевірка платіжного модуля замовлення була `empty($method) && $method->module !== ...` — з `&&`
  вона не спрацьовувала ніколи, і колбек проходив для замовлення, оплаченого через інший модуль.
  Тепер `||`.
- Збережений id платежу вимагається явно: без нього порівняння зводилось до `null !== null`, тобто
  не перевіряло нічого. Саме порівняння — через `hash_equals()`.
- Тіло колбека валідується перед використанням (`is_object`, наявність і числовий тип
  `details.amount`).
- `CURLOPT_SSL_VERIFYPEER` увімкнено: ключ мерчанта йде в заголовку `Authorization`, і без
  перевірки сертифіката MITM читав би його відкритим текстом.

### LiqPay і Fondy

Перевіряють підписи коректно й змін не потребують.
