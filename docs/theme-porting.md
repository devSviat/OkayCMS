# Перенесення теми на цей форк

Ви маєте тему для стокової OkayCMS і хочете поставити її на цей форк. Вона запуститься й
виглядатиме правильно — але кошик, обране, порівняння, зворотний звʼязок і підписка мовчки
перестануть працювати: HTTP 200, порожня консоль, порожній лог.

Причина одна, і поки вона не зрозуміла, решта документа виглядає як безпідставна вимога.
Тому спершу про неї.

---

## Навіщо це зроблено

### Посилання виконує не лише той, хто його натиснув

У стоковій OkayCMS додавання й видалення з кошика — звичайні адреси:

```
GET /cart/17           додати варіант 17
GET /cart/remove/17    прибрати варіант 17
```

Здається зручним. Проблема в тому, що **GET-адресу відкриває будь-хто, кому вона трапилась**,
і згоди у відвідувача ніхто не питає:

```html
<!-- цього досить на будь-якій сторінці в інтернеті -->
<img src="https://ваш-магазин.com/cart/remove/17" width="1" height="1">
```

Браузер вашого покупця побачить `<img>`, піде за адресою й **надішле ваші куки разом із
запитом** — бо для нього це звичайне завантаження картинки з вашого домену. Кошик спорожніє.
Покупець не клікав нічого; він просто читав чужу сторінку.

Тегом `<img>` це не обмежується. Ту саму адресу відкриють:

- **префетч браузера** — Chrome підвантажує посилання, на які, за його оцінкою, зараз клікнуть;
- **краулер пошуковика** — обходить усе, що знайшов у розмітці;
- **прев'ю в месенджері** — надішліть посилання в чат, і сервіс відкриє його, щоб зібрати
  картинку та опис;
- **сканер пошти й антивірус** — перевіряють посилання в листі, відкриваючи їх.

Жодне з цього не є атакою. Просто **GET за домовленістю нічого не змінює** — на цьому
побудована вся інфраструктура інтернету, і вона поводиться з такими адресами відповідно.
Мутація на GET порушує цю домовленість, і далі вже байдуже, чи є в історії зловмисник:
досить звичайного обходу сайту.

### Чому самого POST замало

POST прибирає випадкове спрацювання: ні `<img>`, ні краулер, ні префетч POST не надсилають.

Але навмисне — лишається. Форму, що надсилає POST на чужий домен, ніщо не забороняє:

```html
<form action="https://ваш-магазин.com/cart/remove/17" method="post">
<script>document.forms[0].submit()</script>
```

Відвідувач відкриває сторонню сторінку — форма надсилається сама, куки знову їдуть з нею.
Це і є CSRF: чужий сайт діє від імені вашого покупця.

Тому потрібне щось, чого стороння сторінка **не може дізнатись**: випадкове значення, яке
магазин видав саме цьому відвідувачу й тримає в його сесії. Це і є `customer_csrf_token`.
Чужий домен не може його прочитати — цьому заважає та сама межа походження, яка не дає йому
читати ваші куки.

Токен живе стільки, скільки сесія: він не одноразовий і після кожної форми не змінюється.
Для захисту від CSRF цього досить — потрібно, щоб чужий сайт його не **знав**, а не щоб він
щоразу був новим.

### Чому куку токена видно скриптам

Токен лежить у двох місцях: у формах як прихованому полі й у куці `okay_csrf`, яка
**навмисно не `HttpOnly`**. Це виглядає як помилка, але ні: кука існує саме для того, щоб
ваш власний JS міг прочитати токен і покласти його в ajax-запит. Читати її може лише скрипт
із вашого домену — чужому це недоступно.

Кука має `SameSite=Lax`, тож у міжсайтовому POST браузер її взагалі не надішле — це другий
шар, незалежний від токена. Покладатись лише на нього не варто: `Lax` рятує від чужої
сторінки, але не від піддомену, яким ви не керуєте, і поводиться по-різному в старих
браузерах.

Решта кук магазину (`shopping_cart`, `wishlist`, `comparison`, `browsed_products`) навпаки
отримали `HttpOnly` і зі скрипта більше не читаються.

І ще: токен їде **тільки в тілі запиту, ніколи в рядку адреси**. В URL він осів би в логах
сервера, в історії браузера й у заголовку `Referer` при переході на сторонній сайт — тобто
перестав би бути таємницею.

## Що саме змінилось у рушії

| Адреса або форма | Було | Стало |
| ---------------- | ---- | ----- |
| `/cart/{variantId}` | GET | POST + токен |
| `/cart/remove/{variantId}` | GET | POST + токен |
| `/ajax/cart_ajax.php` | GET | POST + токен |
| `/ajax/wishlist.php` | GET | POST + токен |
| `/ajax/comparison.php` | GET | POST + токен |
| `/ajax/subscribe` | POST | POST + токен |
| форма зворотного звʼязку | POST | POST + токен |
| форма коментаря | POST | POST + токен |

**Коди відмови:** GET на мутацію → `405`, немає токена або він невірний → `403`.

Параметри цих запитів читаються з `$_POST`. Тема, що надсилає їх у рядку запиту, отримає
`403` або `405` — і на вигляд це буде просто «кнопка не працює».

Двигунова частина змін — [UPGRADE-security.md](UPGRADE-security.md).

## Готовий приклад: `design/okay_shop`

Тема `design/okay_shop` у цьому репозиторії — **та сама стокова тема, уже перенесена**. Її
можна не читати цілком: достатньо подивитись, чим саме вона розходиться зі стоковою, і це
буде рівно той обсяг роботи, що чекає на вашу.

```bash
git remote add upstream https://github.com/OkayCMS/OkayCMS.git   # один раз
git fetch upstream
git diff upstream/master main -- design/okay_shop
```

Розходження — 32 файли, з них додано два: `html/share.tpl` і `html/social_icon.tpl`. Решта
30 — правки наявних. Це і є масштаб роботи, яка чекає на вашу тему: не переписування, а
точкові зміни в шаблонах, які вже є.

Причин у цих файлів пʼять, і вашої теми стосуються перша й пʼята.

**1. Вимога безпеки — те, заради чого цей документ (8 файлів):**

| Файл | Що зроблено |
| ---- | ----------- |
| `js/okay.js` | токен і POST у шести мутуючих ajax-викликах |
| `html/cart_purchases.tpl` | видалення рядка кошика: посилання → POST-форма з токеном |
| `html/pop_up_cart.tpl` | те саме у спливному кошику |
| `html/feedback.tpl` | токен у формі зворотного звʼязку |
| `html/password_remind.tpl` | три стани замість одного (53 рядки → 98) |
| `lang/{ua,ru,en}.php` | 6 ключів для тієї форми |

**2. Перехід рушія на Smarty 5 (6 файлів).** До безпеки стосунку не має, але вашу тему
зачепить так само, якщо вона написана під Smarty 3:

- `login.tpl`, `register.tpl`, `user.tpl`, `wishlist.tpl` — `{$meta_title = … scope=global}`
  загорнуто в `{if empty($meta_title)}`;
- `cart_deliveries.tpl`, `user_deliveries.tpl` — `{implode(',', $arr)}` замінено на
  `{join($arr, ',')}`.

Повний перелік пасток Smarty 5 — у [templates.md](templates.md).

**3. Апстрімні баги, виправлені тут (2 файли).** Вашої теми не стосуються, але якщо ви
копіювали ці шматки зі стокової — стосуються:

- `product_list.tpl` — шаблон звіряв `$controller` зі значенням `Comparison`, тоді як
  контролер називається `ComparisonController`; порівняння через це не відкривало галерею;
- `breadcrumb.tpl` — гілка хлібних крихт для `LoginController` із
  `$smarty.get.action == "password_remind"`, тобто для маршруту, якого немає ні тут, ні в
  стоковій.

**4. Обслуговування форку (4 файли).** Ні на що не впливає: посилання на документацію в
`css.php` та `js.php`, перекладений коментар у `theme-settings.css`, вставка
`{$debug_bar_inline_assets}` в `index.tpl`.

**5. Іконки соцмереж — власні SVG, а не іконковий шрифт (11 файлів).** Бібліотеки
`js_libraries/` у форку немає: розмітку кнопок «поділитися» віддає сервер, а гліфи для них і
для посилань магазину у футері бере `html/social_icon.tpl`. Вашої теми це стосується
напряму — див. [крок 7](#7-кнопки-поділитися-віддає-сервер).

## Що зробити у своїй темі

Сім кроків. Зразок кожного — у `design/okay_shop` і `design/vibe_shop`.

### 1. Токен у кожній формі, що щось змінює

У формах будуть два токени. Вони захищають від різного:

- **`customer_csrf_token`** — від чужого сайту. Браузер сам додає куки покупця до будь-якого
  запиту, тож стороння сторінка може надіслати запит у ваш магазин від його імені.
- **`form_token`** (крок 4) — від зайвої відправки. Подвійний клік чи `F5` створюють другу
  заявку. Зловмисника тут немає, запит справжній, просто зайвий.

Перший другого не замінює: подвійний клік несе правильний `customer_csrf_token`, бо надіслала
його справді ваша форма. Детальніше — [modules/frontend.md](modules/frontend.md#навіщо-їх-два).

`AbstractController` кладе змінну `customer_csrf_token` у **кожен** шаблон вітрини, тож
жодної підготовки не потрібно — просто додайте поле:

```smarty
<form method="post" action="...">
    <input type="hidden" name="customer_csrf_token" value="{$customer_csrf_token|escape}">
    ...
</form>
```

Стосується форм кошика, зворотного звʼязку, коментаря, підписки — усього, після чого на
сервері щось змінюється. Форми пошуку й фільтрів це не зачіпає: вони нічого не змінюють.

**Перевірка обовʼязкова, і перелік форм із часом зріс.** Спершу її мали кошик, обране,
порівняння, зворотний звʼязок і підписка через ajax. Тепер її мають також:

| Форма | Шаблон-зразок |
| ----- | ------------- |
| Зворотний дзвінок | `html/callback.tpl` |
| Коментар до товару | `html/product.tpl` |
| Коментар до запису блогу | `html/post.tpl` |
| Підписка | `html/index.tpl`, `html/blog_sidebar.tpl` |
| Швидке замовлення | `Okay/Modules/OkayCMS/FastOrder/design/html/fast_order_form.tpl` |
| **Вхід** | `html/login.tpl` |
| **Реєстрація** | `html/register.tpl` |

Підписку легко проґавити: токен їй доклеює JS, тож форма виглядає робочою. Але вона не має
`action`, і при вимкненому чи збійному JS сабмітиться нативно — уже без токена. Тому поле
має бути і в розмітці.

Форма без цього поля отримає **403 Forbidden**, і запис не створиться. Якщо ви портували тему
раніше — саме ці форми треба перевірити першими: у стоковій темі поля в них немає.

> **Вхід і реєстрація — окрема увага.** Раніше `/user/login` і `/user/register` приймали POST
> без токена, і тема, що не друкувала поле, працювала. Тепер ні: без поля **користувач не
> зможе ні увійти, ні зареєструватись** — форма поверне `403 Forbidden`. Це найпомітніший з
> усіх пунктів цієї сторінки, бо ламає не крайній випадок, а вхід у магазин. Зразок —
> `design/vibe_shop/html/login.tpl` і `design/vibe_shop/html/register.tpl`.
>
> Другий рубіж на цих двох маршрутах шаблону не стосується: застосунок звіряє ще й заголовок
> `Origin` (із запасним `Referer`). Тема тут нічого не робить — але якщо ви тестуєте вхід
> інструментом, який цих заголовків не шле (`curl` без `-H`, старий HTTP-клієнт), він
> отримає `403` навіть із правильним токеном. Це не дефект теми.

### 2. Токен у кожному ajax, що щось змінює

Прочитайте токен із куки:

```javascript
function okayCsrfToken() {
  var match = document.cookie.match(/(?:^|;\s*)okay_csrf=([0-9a-f]{64})/);
  return match ? match[1] : "";
}
```

І додайте його в дані запиту, разом із `type: "post"`:

```javascript
$.ajax({
  url: okay.router["cart_ajax"],
  type: "post",
  data: {
    action: "add",
    variant_id: variantId,
    customer_csrf_token: okayCsrfToken()
  }
});
```

Було — те саме без двох останніх рядків і без `type`. Саме цих двох рядків і бракує темі,
яка «мовчки не працює».

Якщо десь ви дописуєте токен до вже серіалізованої форми, робіть це в тілі:

```javascript
data: $(form).serialize() + "&customer_csrf_token=" + okayCsrfToken()
```

### 3. Видалення з кошика — форма, а не посилання

Було:

```smarty
<a href="{url_generator route="cart_remove_item" variantId=$purchase->variant->id}">×</a>
```

Стало:

```smarty
<form method="post" action="{url_generator route="cart_remove_item" variantId=$purchase->variant->id}">
    <input type="hidden" name="customer_csrf_token" value="{$customer_csrf_token|escape}">
    <button type="submit">×</button>
</form>
```

**Обережно з версткою кошика.** Якщо рядок товару рендериться всередині форми оформлення,
вкладена `<form>` не спрацює: браузер викидає вкладений відкривальний тег, а її `</form>`
закриває зовнішню форму — і все, що оголошене нижче, включно з кнопкою «Оформити», лишається
без форми. У такому разі замість вкладеної форми поставте кнопку з `formaction`:

```smarty
<button type="submit" formmethod="post" formnovalidate
        formaction="{url_generator route="cart_remove_item" variantId=$purchase->variant->id}">×</button>
```

Вона надішле зовнішню форму на адресу видалення; токен там уже є, решта полів ігнорується.
Так зроблено в `design/vibe_shop/html/cart_purchases.tpl`.

### 4. Одноразовий токен у формах, що пишуть

`customer_csrf_token` захищає від підробки запиту, але не від **повтору** того самого. Подвійний
клік, `F5` на сторінці результату, повтор після таймауту — усе це створювало другий рядок і другий
комплект листів. Для цього є окреме поле, і додає його плагін:

```smarty
{form_token name="callback"}
```

Він друкує готовий `<input type="hidden" name="form_token" value="…">`. Імʼя поля одне на всі
форми, а значення — нове на **кожен показ форми**. Сервер памʼятає, які токени вже спрацювали,
і другий запит із тим самим відсіює.

Звідси й поведінка: дві вкладки з тією самою формою мають різні токени, тож обидві працюють, а
подвійний клік шле один токен двічі й дає один запис.

| Форма | `name=` | Шаблон-зразок |
| ----- | ------- | ------------- |
| Оформлення замовлення | `checkout` | `html/cart.tpl` |
| Зворотний дзвінок | `callback` | `html/callback.tpl` |
| Зворотний звʼязок | `feedback` | `html/feedback.tpl` |
| Коментар до товару й запису блогу | `comment` | `html/product.tpl`, `html/post.tpl` |
| Швидке замовлення | `fast_order` | модуль `OkayCMS/FastOrder` |

Підписки в таблиці немає свідомо: другий запит із тим самим email рядка й так не створює — його
відсіює перевірка унікальності.

Атрибут `name` обовʼязковий. Без нього плагін нічого не друкує, лише лишає в розмітці
`<!-- form_token: не вказано name -->` і попередження в лог, — форма при цьому втрачає захист.

**Саме поле не обовʼязкове.** Без нього тема працює: тоді повтором вважається та сама
відправка протягом хвилини (для оформлення — десяти). Такий спосіб грубіший, тому поле краще
додати.

Повтор не показує помилку. Заявка й відгук покажуть те саме підтвердження, що й перша
відправка, а оформлення приведе на сторінку вже створеного замовлення: для покупця дія
відбулась, і другого підтвердження він не просив.

> Поле `checkout_token`, яке було в ранній версії форку, більше не читається. Якщо ваша тема
> його має — замініть на `{form_token name="checkout"}`.

### 4.1. Код помилки `not_saved`

Якщо запис не пройшов, форма коментаря й зворотного зв'язку більше не показують успіх — вони
перемальовуються з `$error == 'not_saved'`. Додайте цей код у свій блок помилок:

```smarty
{elseif $error=='not_saved'}
    <span data-language="form_error_not_saved">{$lang->form_error_not_saved}</span>
```

Рядок `form_error_not_saved` є в `design/<тема>/lang/{ua,ru,en}.php` обох тем — до себе візьміть
звідти. Тема без цієї гілки покаже порожню плашку помилки: покупець побачить, що щось не так,
але не зрозуміє що.

### 5. Сторінка відновлення пароля

Раніше посилання з листа одразу впускало користувача в кабінет. Тепер воно веде на форму
нового пароля — а отже, шаблон має обробити **три** стани:

| Стан | Що показати |
| ---- | ----------- |
| `$recovery_expired` | посилання протерміноване, запропонувати надіслати новий лист |
| `$recovery_mode` | форма нового пароля: `new_password`, `new_password_check`, `reset_password=1` |
| ні те, ні те | звичайна форма «надішліть мені лист» |

Мовні ключі, які треба додати в `lang/{ua,ru,en}.php` — усі три файли, інакше в одній мові
буде порожньо (зразок: `design/okay_shop/lang/ua.php`):

`password_remind_letter_sent_generic`, `password_remind_expired`,
`password_remind_password_empty`, `password_remind_password_wrong`,
`password_remind_new_password`, `password_remind_save`.

### 6. Куки більше не читаються зі скрипта

`shopping_cart`, `wishlist`, `comparison`, `browsed_products`, `userReferer`, `last_position`
отримали `HttpOnly`. Якщо ваш JS читав їх через `document.cookie`, він тепер отримує порожньо
й теж без помилки. Замініть це на `data-`-атрибут, який рендерить сервер.

Виняток єдиний — `okay_csrf`, і причина описана вище.

### 7. Кнопки «поділитися» віддає сервер

Каталогу `js_libraries/` у форку немає. Порожній контейнер, який наповнювала бібліотека, і
її ініціалізація в `scripts.tpl` нічого не роблять — приберіть їх:

```smarty
{* Було *}
<div class="fn_share jssocials share__icons"></div>
```

```smarty
{* І в scripts.tpl — теж було *}
$(".fn_share").jsSocials({ shares: {$settings->sj_shares|json_encode} });
```

Замість цього зробіть у темі `html/share.tpl`. Список мереж і готові адреси віддає плагін
`{share_links}`; підпис лишайте в розмітці й обрізайте візуально — це доступна назва кнопки:

```smarty
{share_links var=shareLinks url=$url title=$title}
{if $shareLinks}
    <div class="share__list">
        {foreach $shareLinks as $link}
            <a href="{$link.url|escape}"{if $link.blank} target="_blank" rel="noopener nofollow"{/if}>
                {* ваш гліф за $link.key *}
                <span class="sr-only">{$link.label|escape}</span>
            </a>
        {/foreach}
    </div>
{/if}
```

`$link.blank` вішайте саме так, а не безумовно: `email` віддається поштовому клієнту
(`mailto:`), `viber` — застосунку (`viber://`), і нова вкладка в обох випадках лишається
висіти порожньою. Прапорець рахує `SocialShare` зі схеми адреси, тож у шаблоні його
перевіряти не треба.

Викликайте його там, де стояв контейнер: `{include file="share.tpl" url=$canonical title=$h1}`
на товарі й `url=$canonical title=$post->name` у пості.

Гліфи бібліотека брала з FontAwesome, а там немає ні X, ні Viber, ні LINE — на місці X
показувалась стара пташка Twitter. Обидві теми форку тому возять власні SVG і мапу
`html/social_icon.tpl`, яка перетворює назву мережі на гліф:

```smarty
{$socialIcons = ['facebook' => 'social_facebook', 'twitter' => 'social_x', ...]}
{include file="svg.tpl" svgId=$socialIcons[$domain|default:''|lower]|default:'social_link'}
```

Той самий файл обслуговує і посилання магазину у футері — туди приходить домен, витягнутий
з адреси, тож у мапі поруч із `telegram` стоїть ще й `t`, а поруч із `youtube` — `youtu`.
Невідома мережа має отримувати запасний гліф, а не порожнечу.

Ключі мереж перелічені в `Okay\Core\SocialShare`. Стиль гліфів беріть від своєї теми:
`vibe_shop` малює контуром (Tabler, 24×24, `stroke-width="1.8"`), `okay_shop` — заливкою
(Simple Icons, 24×24, `fill="currentColor"`).

Налаштування `social_share_theme` більше не використовується: пʼять його значень були
іменами CSS-файлів бібліотеки. Кнопки оформлює тема.

## Як переконатись, що тема жива

**Зелені тести цього не доводять — жодної сторінки вони не відкривають.** Пройдіть руками:

1. додати товар у кошик із картки й зі сторінки товару;
2. змінити кількість, видалити рядок;
3. купон, вибір доставки, оформлення замовлення — і окремо: **надішліть форму оформлення двічі**,
   друге надсилання має привести на сторінку створеного замовлення, а не створити друге;
4. обране: додати й прибрати;
5. порівняння: додати й прибрати;
6. зворотний звʼязок, коментар, підписка;
7. відновлення пароля — до листа й далі за посиланням із нього.

**`403` означає загублений токен. `405` — що форма пішла методом GET.**

Якщо тримаєте свою тему в цьому репозиторії, додайте її в провайдер
`tests/Security/StorefrontCsrfGuardTest.php` — він перевіряє, що в темі є `okayCsrfToken`
і що всі мутуючі виклики через нього проходять.
