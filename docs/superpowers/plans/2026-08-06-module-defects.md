# Чотири напрями: дефекти модулів фідів, LiqPay і те, що віддається з кореня

**Статус:** беклог, не план виконання. Нічого з описаного тут не зроблено.

**Звідки числа:** усе перевірене в цьому репозиторії — код, дев-база й `SHOW INDEX`, а не
переказане з наміру. Порядок пунктів — за наслідком, а не за розміром правки.

---

## 1. Приватний ключ мерчанта LiqPay доїжджає до браузера покупця

`Okay/Modules/OkayCMS/LiqPay/PaymentForm.php:65` кладе `private_key` у `$data_array`:

```php
$data_array = [
    'version'      => 3,
    'public_key'   => $publicKey,
    'private_key'  => $privateKey,   // <-- сюди
    ...
];
$data = base64_encode(json_encode($data_array));
$sign = base64_encode(sha1($privateKey.$data.$privateKey, 1));
```

`$data` рендериться в `design/html/form.tpl:2` як `<input type="hidden" name="data">`. Base64 —
це **кодування, а не шифрування**: будь-хто, хто дійшов до сторінки оплати, читає ключ із
вихідного коду сторінки.

Наслідок не в самому розкритті. Підпис колбека рахується тим самим ключем
(`sha1($privateKey.$data.$privateKey)`), тож маючи ключ, можна підписати підроблений колбек і
позначити замовлення оплаченим, не заплативши. У протоколі LiqPay v3 приватний ключ у складі
`data` не потрібен взагалі — лише для обчислення підпису на сервері.

**Що зробити:**

- прибрати `private_key` з `$data_array`;
- підпис продубльований інлайном у `PaymentForm.php` і в `Controllers/CallbackController.php`,
  а кожна гілка контролера завершується `exit;` — тобто без виносу підпису в окремий клас
  тестом його не накрити. Винести `LiqPaySignature` з `sign()` і розбором `order_id`;
- тест, що payload форми не містить приватного ключа в жодному вигляді (сирому, base64 і в
  json), плюс тест на сам підпис.

**Окремо, не код:** якщо модуль уже працював на бойовому магазині, наявний ключ слід вважати
скомпрометованим і перевипустити в кабінеті LiqPay. Це рішення власника, не наслідок правки.

Дефект прийшов зі стоку — правка стосується форку.

## 2. Порожній масив у фільтрі мовчки віддає весь каталог

`Okay/Core/Entity/filter.php:81`, `autoFilter()`:

```php
if ($value === []) {
    return;
}
```

Тобто `find(['id' => []])` — це **не** «нічого не знайдено», а «фільтра по id немає». У
`ProductsEntity` власного `filter__id` немає, тож працює саме `autoFilter()`.

Три модулі викликають `getList()` з таким масивом без захисту:

| Файл | Рядки |
| ---- | ----- |
| `Okay/Modules/OkayCMS/GoogleMerchant/Helpers/BackendGoogleMerchantHelper.php` | 340, 369 |
| `Okay/Modules/OkayCMS/Hotline/Helpers/BackendHotlineHelper.php` | 340, 369 |
| `Okay/Modules/OkayCMS/Rozetka/Helpers/BackendRozetkaHelper.php` | 340, 369 |

Поки в таблиці зв'язків немає жодного рядка типу `product` — а це стан свіжо встановленого
модуля, — вироджуються **обидва** виклики, тобто два повні проходи каталогу на один рендер
сторінки. На каталозі дев-бази (227 товарів) це непомітно; на бойовому це секунди.

Правильний зразок уже є в цьому ж репозиторії —
`Okay/Modules/OkayCMS/Feeds/Backend/Helpers/BackendFeedsHelper.php:221`:

```php
$condition->entities = empty($condition->entity_ids) ? [] : $this->productsHelper->getList(['id' => $condition->entity_ids]);
```

**Питання, яке треба вирішити до правки:** лікувати кожного викликача чи саме ядро. Мовчазне
викидання порожнього масиву — пастка загальна, і наступний модуль наступить на неї так само.
Але зміна `autoFilter()` на «порожній масив = порожній результат» зачіпає **все**, що передає
масиви у фільтри, і може мовчки змінити поведінку сторінок, які зараз на цьому виродженні
тримаються. Мій нахил: спершу захист у трьох викликачах, окремо — тест-запобіжник, який
фіксує поточну поведінку ядра, і лише потім розмова про ядро.

## 3. Та сама сторінка читає таблицю зв'язків чотири рази

У тих самих трьох хелперах, рядки 291, 310, 330, 359 — чотири окремі `find()` по таблиці
зв'язків, кожен із `['limit' => $this->relationsEntity->count()]`, тобто ще й із зайвим
`COUNT(*)` на кожен виклик. Читається одна й та сама таблиця, різниться лише
`entity_type`/`include`.

Індекс на ній непридатний для цих вибірок. У дев-базі
`ok_okaycms__google_merchant__relations` має рівно один неунікальний індекс:

```
feed_id_entity_type_include_entity_id  ->  feed_id, entity_type, include, entity_id
```

Провідна колонка — `feed_id`, а адмінка фільтрує по `entity_type` (і `include`) **без**
`feed_id`. Тобто індекс не використовується взагалі.

**Що зробити:**

- згорнути чотири читання в одне з кешем на час запиту;
- додати індекс `(entity_type, include, feed_id)` через `update_1_0_1()`; усі три модулі зараз
  версії `1.0.0`, тож потрібен і підйом версії в `module.json`. У `update_x_y_z()` немає DI —
  сервіси через `ServiceLocator`, як велить `docs/modules/lifecycle.md`;
- прибрати `['limit' => $entity->count()]` на користь `noLimit()`. Це не косметика: пара
  «COUNT + LIMIT» замість одного запиту, і при паралельній вставці між ними частина рядків
  губиться. Таких місць рівно **24** — по вісім у кожному з трьох модулів, разом із
  `Backend/Controllers/*Admin.php` і `Extenders/BackendExtender.php`
  (`grep -rn "'limit' => .*count()" Okay/Modules/`).

## Головне про обсяг

`BackendGoogleMerchantHelper.php`, `BackendHotlineHelper.php` і `BackendRozetkaHelper.php` —
**побайтово однакові**, по 377 рядків кожен; різняться лише імена класів і неймспейси.
Перевірено `diff` із заміною імен: нуль розбіжностей. Тому пункти 2 і 3 — це одна правка,
застосована тричі, і три однакові набори тестів.

Спокуса винести спільний предок велика, але це зміна архітектури трьох модулів заради
косметики; за правилами форку модуль не править чужі файли, а спільний батько мусив би жити в
ядрі. Мій нахил: цього разу тричі однаково, а винос — окремою розмовою.

## Дрібниця — вже зроблено в цій же гілці

`.gitignore` містив `robots.txt`. Правило було мертве — git не застосовує ігнор до вже
відстежуваних файлів, а файл відстежується з `6ac644ea`. Але саме воно приглушувало файл у
git-панелях редакторів (виглядав як невідстежуваний) і зробило б випадкове `git rm --cached`
незворотним: повернути вийшло б лише через `-f`. Рядок замінено коментарем, чому файл навмисно
в репозиторії: статику в корені віддає nginx зі свого образу, і `dev/bin/smoke-prod.sh:160`
пробує саме цей файл, щоб довести, що дерево застосунку на місці.

## 4. Що віддається з кореня як статика — потрібен аудит

`dev/config/nginx/templates/default.conf.template` побудований як **чорний список**: перелічує
те, що заборонено (`composer.(json|lock)`, `phpunit.xml`, кореневі `*.md|neon|lock|yml|dist|
sh|toml`, `config/`, `dev/`, `tests/`, `1DB_changes/`, `Okay/`, `docs/`). Такий підхід
неповний за побудовою: будь-який новий файл у корені віддається за замовчуванням.

Перевірено на працюючому оточенні (`curl` до `http://localhost/`), **не гіпотези**:

| Шлях | Код | Що витікає |
| ---- | --- | ---------- |
| `/vendor/composer/installed.json` | **200** | 248 КБ: **усі залежності з точними версіями**, git-посилання й хеші. Готовий перелік для добору CVE — це гірше за `composer.json`, який уже заборонений |
| `/ok` | **200** | вихідний код точки входу консолі: `Okay\Core\Console\Application`, `ServiceLocator`, внутрішні коментарі. Розширення немає, тож правило по розширеннях його не ловить |
| `/vendor/bin/phpunit` | **200** | те саме — файл без розширення |
| `/vendor/autoload.php` | **200** | PHP **виконується** під `vendor/`; у відповіді `X-Powered-By: PHP/8.5.9` |
| `/vendor/composer/ClassLoader.php` | **200** | те саме |
| `/vendor/smarty/smarty/src/Smarty.php` | **500** | вендорний файл як точка входу: помилка в лозі на кожен такий запит |

Заборонені й повертають 404: `composer.json`, `composer.lock`, `phpunit.xml`, `phpstan*.neon`,
`phpcs.xml.dist`, усі кореневі `*.md`, `config/`, `dev/`, `tests/`, `docs/`, `1DB_changes/`,
`.git/`, `.github/`.

Заголовки віддають зайве: `X-Powered-By: PHP/8.5.9` (точна версія PHP) і `X-Powered-CMS:
OkayCMS`.

**Що зробити:** перевернути логіку — білий список кореневих файлів замість переліку заборон.
Віддавати з кореня рівно `robots.txt`, `favicon.ico`, `sitemap.xml` і `.well-known/`, решту
кореня закрити; `vendor/` закрити цілком, включно з виконанням PHP; прибрати `X-Powered-By`.

**Окремо:** `docs/nginx/nginx.conf` — приклад, на який посилаються `docs/README.md` і
`docs/UPGRADE-security.md`, — не забороняє нічого з переліченого, ще й указує неіснуючий
`root_path /application/public`. Його треба привести у відповідність тим самим рішенням.
