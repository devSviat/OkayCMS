# Self-update ядра форку: перевірка й встановлення оновлень з адмінки

**Дата:** 2026-08-30

## Задача

`Okay/Core/Config.php` містить лише одне жорстко закодоване поле версії
(`$version = '4.5.2'`, upstream-база) — жодного механізму, що порівнює
поточний стан інсталяції з новішим релізом і накочує різницю, немає.
`1DB_changes/*.sql` — 54 файли, з яких автоматично застосовується лише
`okay_clean.sql`, і тільки для чистого встановлення (`ok database:deploy`);
послідовних `update_X.Y.Z.sql` для існуючої інсталяції не прогонить ніщо.
Єдиний реально працюючий версійно-керований апдейтер у кодовій базі —
`Okay/Modules/OkayCMS/AutoDeploy` — розрахований на Bitbucket-webhook +
`git pull` + Phing на сервері з `.git`-доступом; ні GitHub, ні пакетів,
ні checksum там немає, і застосовність обмежена per-module апдейтами
(`Installer::update()`).

Мета: дати власнику типової (без Docker, файли на диску, `www-data` пише
напряму) інсталяції форку кнопку "Оновити" в адмінці, яка перевіряє GitHub
Releases репозиторію `devSviat/OkayCMS`, знаходить лише **релізи форку**
(не апстрім-теги), і безпечно накочує новий core-код + core-міграції з
backup і rollback при невдачі.

## Область застосування

**Всередині:** ядро форку (`Okay/Core`, `Okay/Controllers`, `Okay/Entities`,
`Okay/Helpers`, `Okay/Requests`, `backend/` крім теми адмінки,
`Okay/Modules/OkayCMS/*`, `composer.json`/`.lock`, `ok`, `index.php`) і
core-специфічні DB-міграції нового зразка (§7).

**Поза межами (свідомо):**
- `Okay/Modules/Sviat/*`, `Okay/Modules/Broken/*` та будь-які сторонні
  модулі — своя система синхронізації через okay-lab (див. пам'ять
  `okay-lab-module-sync-workflow`), self-updater їх не чіпає.
- `design/*` (теми вітрини) і `backend/design/*` (тема адмінки) —
  виключені з core-пакету взагалі (§5, edge case).
- Контейнеризований prod-деплой `broken` (build-images.yml → GHCR →
  Dokploy, `DEPLOY.md`) — окрема, вже робоча система. Self-updater на
  `broken` використовується **тільки в dev-оточенні** (bind-mount коду),
  результат комітиться й пушиться вручну, далі йде вже наявний pipeline.
  Це рішення обговорено і підтверджено з користувачем окремо від цього
  документа; тут фіксується лише висновок.
- Підпис релізів (Sigstore/GPG) — v2, нижче в §12 як відкладене рішення,
  не блокує v1.

## Термінологія

- **Fork version** — власна лінійка форку, тег `okaycms-fork/vX.Y.Z`
  (SemVer). Зберігається як нове поле `Okay\Core\Config::$forkVersion`.
- **Upstream base** — версія апстріму OkayCMS, яку конкретний реліз форку
  ввібрав (існуюче поле `Config::$version`, семантика не міняється).
- **Core package** — zip-архів одного релізу форку, вміст описаний у §6.
- **Core migration** — `.up.sql`-файл всередині пакету релізу, застосовується
  новим трекером `ok_core_migrations` (§7), не плутати зі старими
  `1DB_changes/*.sql`.

## 1. Версіонування і теги

- Апстрім-теги `4.x.x` лишаються недоторканими, як зараз, і **ніколи не
  отримують GitHub Release-обгортку** — тільки голий git tag.
- Нова паралельна послідовність тегів `okaycms-fork/vX.Y.Z` ставиться на
  комітах `main`, які проходять реліз-пайплайн (§3). Перший —
  `okaycms-fork/v1.0.0` на поточному HEAD (`$version = '4.5.2'`).
- `Config::$forkVersion` — нове публічне поле поруч з `$version`, частина
  core-пакету (оновлюється звичайним перезаписом файлу разом з рештою
  core-коду на кроці "apply", окремого version-файлу поза кодом не
  заводимо — простіше і не розходиться з поточним підходом).

## 2. Розрізнення fork-релізів і апстрім-тегів через GitHub API

`GET /repos/devSviat/OkayCMS/releases` — не `/tags`. Оскільки апстрім-теги
без Release-обгортки в цей ендпоінт не потрапляють органічно,
додаткового фільтрування на клієнті для базового випадку не потрібно.
Захисний фільтр все одно лишаємо: `tag_name` мусить збігатись з
`^okaycms-fork/v\d+\.\d+\.\d+$`, будь-який запис, що не збігається,
ігнорується мовчки (лог на debug-рівні) — на випадок, якщо хтось колись
помилково створить Release на апстрім-тезі.

## 3. GitHub Actions: `release.yml`

Тригер — push тегу `okaycms-fork/v*`.

```
checkout
composer install --no-dev --optimize-autoloader
той самий тестовий набір, що й ci.yml — включно з composer audit
  (реалізовано ручною копією джоби tests, бо ci.yml не має
  workflow_call; борг: винести спільні кроки в composite action,
  щоб не розходитись — розходження вже один раз сталося)
build:
  - зібрати core-дерево за explicit allow-list з release-manifest.json (§5)
  - version.json:   {forkVersion, upstreamBase, minPhp, releasedAt,
                      requiresMigrations: bool}
                    minPhp — конкретна нижня межа версії (8.4.0),
                    нормалізована з composer-констрейнта, придатна
                    для version_compare()
  - manifest.json:  повний список core-шляхів у пакеті, sha256 на кожен файл
  - okaycms-fork-vX.Y.Z.zip
  - checksums.txt:  sha256 на сам zip і на version.json окремо
gh release create okaycms-fork/vX.Y.Z
  --title, --generate-notes (нотатки генерує GitHub з PR/комітів
                             діапазону; окремий CHANGELOG.md не ведемо)
  --attach okaycms-fork-vX.Y.Z.zip
  --attach checksums.txt
  --attach version.json   (некомпресований, окремий asset — щоб
                            "перевірити оновлення" не тягнуло весь zip)
```

Токен для цього кроку — вбудований `GITHUB_TOKEN` Actions, зовнішній
секрет не потрібен.

## 4. Перевірка з адмінки: без токена, з ETag-кешем

Репозиторій публічний → `GET /repos/.../releases` і завантаження asset'ів
не потребують токена. Unauthenticated ліміт — 60 запитів/год на IP;
для перевірки раз на кілька годин з одного сервера цього достатньо, і
додатково:

- **ETag conditional requests** (`If-None-Match`) — GitHub не рахує
  304-відповіді проти ліміту.
- Результат кешується в новій таблиці (§8) на 6 годин (константа,
  налаштовувана через `config.local.php`). Адмінка при заході в розділ
  "Оновлення" читає лише кеш, ніколи не б'є GitHub напряму синхронно з
  рендером сторінки.

Токен (`GITHUB_TOKEN` в `config.local.php`, опціонально) підтримується
на випадок приватного репозиторію в майбутньому або спільного IP з
іншими інсталяціями — не обов'язковий для v1.

## 5. Межа "core" vs "user data"

Explicit allow-list у `release-manifest.json` (корінь форку, комітиться
й рев'юриться як звичайний код), не heuristic "все, крім винятків".

**У пакеті (перезаписується):**
`Okay/Core/`, `Okay/Controllers/`, `Okay/Entities/`, `Okay/Helpers/`,
`Okay/Requests/`, `Okay/lang_general/` (мовні файли ядра),
`Okay/xml/opensearch.xml.tpl`,
`backend/` **крім** `backend/design/` (див. edge case нижче) і **крім**
runtime-writable піддерев (`backend/files/` — користувацькі
вивантаження; аналогічно виключені `Okay/Modules/OkayCMS/AutoDeploy/{log,tmp}/`
та `Okay/Modules/OkayCMS/Integration1C/temp/` — інакше локальна збірка
релізу на живій інсталяції запакувала б клієнтські дані в публічний
asset),
`Okay/Modules/OkayCMS/*`, `composer.json`, `composer.lock`, `ok`,
`index.php`, нові файли `1DB_changes/` (додаються, старі не чіпаються).

Каталогу `Okay/Extenders/` у форку не існує (екстендери живуть у
модулях) — рання версія цього документа помилково його називала.

Кореневі `.htaccess` і `robots.txt` у пакет **не входять** — свідомо.
Для цільової аудиторії (класичний хостинг без Docker) `.htaccess` —
головний важіль безпеки периметра, але він же і найчастіше локально
кастомізований (редиректи, ліміти хостера); мовчки перезаписувати його
оновленням небезпечніше, ніж не доставити правку. Якщо колись
знадобиться доставити критичну зміну `.htaccess` — це буде явний,
окремо задокументований крок міграції в нотатках релізу, не тихий
перезапис.

`vendor/` **не входить у zip** — перегенерується на сервері командою
`composer install` за оновленим `composer.lock` під час apply (§8, крок
apply). Причина: інакше пакет роздувається і несе ризик бінарної
несумісності збірок різних PHP-версій/розширень між середовищами.

**Ніколи не чіпається:** `Okay/Modules/Sviat/*`, `Okay/Modules/Broken/*`
і будь-який вендор, якого немає в `release-manifest.json`, `design/*`,
`backend/design/*`, `config/*`, `files/*`, `cache/*`, `compiled/*`,
`Okay/log/*`.

Updater на боці CMS довіряє **лише** переліку з `manifest.json`
конкретного релізу — якщо шлях не в цьому переліку, він не чіпається,
навіть якщо фізично присутній у zip (defense-in-depth на випадок
помилки в build-кроці).

## 6. Формат пакету оновлення

```
okaycms-fork-v1.1.0.zip
├── version.json     forkVersion, upstreamBase, minPhp, releasedAt,
│                    requiresMigrations
├── manifest.json    повний список core-шляхів пакету + sha256 на кожен
├── migrations/      нові core .up.sql-файли цього релізу (може бути
│                    порожньо)
└── payload/         дзеркало core-дерева, 1:1 зі списком у manifest.json
```

Per-file checksum у `manifest.json` дозволяє звірити цілісність
пофайлово після розпакування (не лише архів цілком) і в майбутньому
підтримати delta-апдейти без зміни формату.

## 7. Core-міграції

Новий, ізольований від `Installer`/AutoDeploy механізм, той самий патерн
"track applied by filename in a DB table", що вже перевірений у
`AutoDeploy::MigrationsEntity`, але власна таблиця:

- `ok_core_migrations` (`id`, `name`, `applied_at`) — створюється
  міграцією самого CoreUpdater-модуля при його першому встановленні.
- Файли `migrations/{fork-version}_{опис}.up.sql` у пакеті релізу —
  застосовуються по черзі, кожен в окремій транзакції, кожен написаний
  ідемпотентно (`CREATE TABLE IF NOT EXISTS`, перевірка через
  `INFORMATION_SCHEMA` перед `ALTER`, де MySQL/MariaDB не підтримує
  `IF NOT EXISTS` для колонки).
- Стара директорія `1DB_changes` цим механізмом не використовується і не
  замінюється — вона лишається для fresh-install (`ok database:deploy`).
  Нові core-diff публікуються тільки через `migrations/` у пакеті релізу.

## 8. Потік оновлення (`CoreUpdater`)

Новий core-модуль `Okay/Modules/OkayCMS/CoreUpdater/` (той самий патерн
модуля, що й AutoDeploy). Він сам входить у "core"-перелік §5 — самозаміна
відбувається на кроці apply так само, як і решта core-файлів: до моменту
запуску apply() працює стара версія модуля, після — нова, наступний
виклик уже піде через оновлений код.

1. **Check** — читання кешу (§4) або ETag-запит, показ
   "Доступна 1.1.0 (на основі 4.6.0)".
2. **Перегляд змін** — рендер `notes` релізу (Markdown → HTML).
3. **Завантаження** — за `browser_download_url` з Releases API (не за
   згаданим URL) у `files/tmp/updates/{version}/` (поза webroot
   allow-list, з урахуванням `docs/UPGRADE-security.md`).
4. **Перевірка цілісності** — sha256 усього zip проти `checksums.txt`;
   після розпакування — sha256 кожного файлу проти `manifest.json`.
   Будь-яка розбіжність — стоп, нічого не застосовується, temp
   видаляється.
5. **PHP-compatibility gate** — `version.json.minPhp` проти
   `PHP_VERSION`, до будь-яких змін у файловій системі чи БД.
6. **Backup** — `zip` лише тих файлів поточного дерева, які будуть
   перезаписані/видалені саме цим релізом (перетин поточного стану з
   `manifest.json` нового пакету, не весь сайт) →
   `files/backups/pre-update-{old}-to-{new}-{timestamp}.zip`.
   Окремо — `mysqldump` тільки тих таблиць, яких торкнуться
   `migrations/` цього релізу (не весь дамп бази).
7. **Maintenance mode** — файл-прапорець (`config/.maintenance`),
   перевіряється в bootstrap до ініціалізації решти CMS, показує
   статичну сторінку. Новий код — зараз такого немає ніде.
8. **Apply (spool-and-swap)** — файли з `payload/` копіюються з
   тимчасової директорії на місце file-by-file, з `rename()` там, де
   джерело й ціль на одній файловій системі (atomic на рівні окремого
   файлу; повний directory rename непридатний, бо частина core-шляхів
   переплетена з user-data в тому самому дереві). Кожен крок пишеться в
   окремий update-лог, не в `Okay/log/app-*.log` — щоб фейл читання
   основного лога не приховав фейл самого apply. Одразу після копіювання
   файлів — `composer install --no-dev` за новим `composer.lock`.
9. **Migrations** — `migrations/*.up.sql` по черзі, кожна своя
   транзакція; фейл однієї зупиняє процес одразу, без спроби
   автоматичного відкату DDL (MySQL DDL здебільшого не транзакційний) —
   перехід напряму до §9 rollback.
10. **Cache/OPcache** — очистка `compiled/`, `backend/design/compiled/`
    (як `make clear`), явний `opcache_reset()` (зараз ніде не
    викликається в кодовій базі), інвалідація об'єктного кешу через
    штатний API кешу за тегами (не сирий `FLUSHALL`/сирий SQL — див.
    пам'ять `redis-flush-auth-and-raw-sql-invalidation`).
11. **Health check** — внутрішній HTTP-запит на легкий endpoint (curl на
    `localhost`), очікує 200 і маркер нової версії в тілі відповіді (щоб
    відсіяти false-positive від кешованої сторінки). Фейл → rollback (§9).
12. **Finalize** — зняття maintenance mode, `files/tmp/updates/{version}/`
    видаляється (backup-архів лишається), запис результату в
    update-лог/БД-статус.
13. **Fail → rollback** — §9.

Progress виноситься в окремий статус-запис (БД/кеш), UI поллить його —
HTTP-запит на "Оновити" не тримається відкритим 30-60 секунд надійно.
Сам процес запускається як CLI (`ok core:update`) або web-запит з
`ignore_user_abort(true)`, щоб не залежати від з'єднання браузера.

## 9. Backup і rollback

- Rollback = розпакувати backup-zip з кроку 6 назад поверх поточного
  дерева, тим самим spool-and-swap у зворотному напрямку.
- Core-міграції **не** відкочуються автоматично (DDL rollback
  ненадійний) — замість цього адміну показується явне попередження з
  переліком застосованих `ok_core_migrations`-записів цього релізу і
  посиланням на SQL-дамп із кроку 6 для ручного відновлення.
- Maintenance mode знімається тільки після успішного health-check **або**
  після завершеного rollback + повторного health-check.
- Зберігаються останні 3 backup-архіви, старіші прибираються автоматично.

## 10. UX в адмінці

```
Встановлено:  OkayCMS Fork 1.0.0  (на основі OkayCMS 4.5.2)
Доступно:     OkayCMS Fork 1.1.0  (на основі OkayCMS 4.6.0)
              [Переглянути зміни]  [Оновити]
```

Прогрес під час apply — поллінг статус-запису (крок 1-13 з §8) окремим
AJAX-запитом, не єдиний довгий HTTP-виклик.

## 11. Edge cases

- **PHP нижче `minPhp`** — блокується на кроці 5 §8, до будь-яких змін.
- **Перерваний апдейт** (обрив з'єднання, вбитий процес) — сам apply не
  залежить від з'єднання браузера (CLI/`ignore_user_abort`); якщо процес
  сервера все ж вбито — при наступному заході в адмінку виявляється
  "недозастосований" стан (maintenance-файл є, статус "in progress") →
  явне повідомлення "Оновлення перервано, потрібне ручне втручання",
  без тихого автоматичного продовження.
- **Одночасні запити під час апдейту** — maintenance mode вирішує це для
  звичайних відвідувачів; сам apply-процес тримає файловий `flock`, щоб
  унеможливити дві паралельні спроби (подвійний клік "Оновити").
- **Кастомізована `backend/design/`** — виключена з core-пакету взагалі
  (§5). Якщо колись знадобляться core-правки саме туди — окремий
  "admin theme asset" реліз поза цим механізмом, не щоденний цикл.
- **Downgrade** — тільки explicit вибір адміном конкретної старішої
  версії зі списку релізів, ніколи автоматично. Якщо на інсталяції вже
  застосовані core-міграції з релізу новішого за цільовий — downgrade
  блокується явним повідомленням (безпечний відкат схеми "назад" не
  гарантується).
- **Replay / підміна релізу заднім числом** — `manifest.json` містить
  `releasedAt`; updater відмовляється застосовувати пакет, чий
  `releasedAt` старіший за вже встановлений `forkVersion`, якщо це не
  explicit downgrade-запит з попереднього пункту.
- **MITM / підміна asset** — HTTPS до GitHub API/CDN як базовий захист;
  checksum з `checksums.txt`, отриманий тим самим TLS-з'єднанням,
  захищає від пошкодження при передачі, але не від компрометації самого
  GitHub-акаунту чи Actions-runner'а. Підпис — окремо, §12.
- **`compiled/` у tmpfs на `broken`** — це не стосується інших
  інсталяцій; `make clear` і так це очищає, для dev-полігону нічого
  додаткового не потрібно.

## 12. Підпис релізів — відкладене рішення (v2)

Не блокує v1. Два варіанти на майбутнє:

- **GPG detached signature** — приватний ключ, підписування кожного
  релізу. Реальний виграш над "checksum з того ж TLS-з'єднання" — лише
  якщо ключ підписується офлайн, поза Actions (інакше компрометація
  Actions ламає і checksum, і підпис однаково).
- **Sigstore/cosign keyless (OIDC)** — короткоживучий сертифікат через
  GitHub OIDC, без довгострокового ключа, публічний Rekor-лог. Верифікація
  на боці CMS вимагає `cosign`-бінарника або REST до Rekor — нова
  залежність, якої зараз немає в PHP-стеку.

**Рішення для v1**: SHA-256 checksum + HTTPS. Достатньо проти MITM і
пошкодження при передачі, найпростіше в підтримці для одноосібного
проєкту. Переоцінити після кількох релізів, якщо з'явиться реальний
привід (зовнішні контриб'ютори з push-правами, публічний дистрибутив
поза GitHub тощо).

## 14. Тестування

- Юніт/інтеграційні тести на: розбір `manifest.json`/`version.json`,
  фільтр релізів за regex тегу, spool-and-swap на тестовому дереві файлів
  (успіх і навмисно пошкоджений пакет), застосування/rollback
  `ok_core_migrations` на тестовій БД (`docs/testing.md` — guard-тести
  цього класу).
- Ручний наскрізний прогін на `broken` у **dev**-оточенні (bind-mount):
  штучний "попередній" fork-реліз (напр. `okaycms-fork/v0.9.0` з мінімальною
  різницею) → апдейт до `v1.0.0` → перевірка застосованих файлів, логів,
  health-check, і окремо — навмисно зіпсований checksum/перерваний
  процес, щоб побачити, що rollback і maintenance-повідомлення
  спрацьовують, а не тихо проходять.
- Контрольний прогін "зламай навмисно": як і для інших перевірок у цьому
  проєкті (див. пам'ять про контроль перевірок) — переконатись, що
  health-check дійсно червоніє на зіпсованій core-міграції, а не завжди
  повертає "ок".

## 15. Верхньорівневий план

1. Підготовка репозиторію на GitHub (гілка `dev`, branch protection,
   перший fork-tag `okaycms-fork/v1.0.0`).
2. `release-manifest.json` + `release.yml` (build+publish, ще без самого
   updater'а) — перевірити, що реліз коректно публікується і відрізняється
   від апстрім-тегів у `/releases`.
3. `Config::$forkVersion` + таблиця `ok_core_migrations`.
4. `CoreUpdater`: check + ETag-кеш (GitHub API), без ще apply.
5. `CoreUpdater`: download → verify → backup → maintenance → apply →
   migrate → cache-clear → health-check → finalize/rollback.
6. Admin UI (сторінка "Оновлення").
7. Наскрізний тестовий цикл на `broken` (dev), включно з навмисним
   зламом (§14).
8. Документація (`docs/updates.md`, допис в `docs/architecture.md`).

Деталізація кожного пункту — окремий implementation plan через
`writing-plans`, з рев'ю на кожному кроці, а не одним махом.
