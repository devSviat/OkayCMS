# Docker environment — audit findings and rebuild for dev, with an optional prod profile

Date: 2026-07-30
Scope: `dev/` (compose files, Dockerfiles, nginx/php/mysql config)
Branch: to be created off `master`
Status: design approved, not implemented

## Problem

The dev environment works, but it works by accident in several places. The audit below was
produced by reading every file under `dev/` and verifying the claims against the running
containers (`OkayCmsDev-php85`, `-nginx`, `-mariadb`, up at the time of the audit).

### Critical

**C1 — the database lives in a bind mount.**
`./mysql/DB_data:/var/lib/mysql` puts 339 MB of InnoDB files inside the repository, kept out of
git only by a line in `dev/.gitignore`. Consequences chain outward:

- `docker/mysql/Dockerfile` exists **solely** to run `usermod -u 1000 mysql` so the container can
  write to a host directory owned by uid 1000. It is hardcoded to 1000; any contributor with a
  different uid gets a container that cannot start.
- `docker compose down -v` does not remove the data, so "reset and reload the dump" requires
  `rm -rf` on a path inside the working tree.
- On macOS and Windows the bind mount is a severe performance penalty for InnoDB.

**C2 — mounting `./config/php` shadows the entire PHP configuration directory.**
Verified inside the running container:

```
$ docker exec OkayCmsDev-php85 ls /usr/local/etc/php/conf.d/
xdebug.ini
```

Every `docker-php-ext-*.ini` file generated by `docker-php-ext-enable` is hidden by the bind
mount. That is why `config/php/php.ini` carries the manual lines `extension = pdo_mysql.so`,
`gd.so`, `zip.so`, `mysqli.so`. The trap: **an extension installed in the Dockerfile silently
fails to load** until someone remembers to add a matching line to `php.ini`.

**C3 — service ports are published on all interfaces.**

```
OkayCmsDev-mariadb   0.0.0.0:3306->3306/tcp
OkayCmsDev-nginx     0.0.0.0:80->80/tcp
```

MariaDB with `root`/`root` is reachable from the whole local network.

### Significant

**S1 — `links:`** is a Compose v1 relic, deprecated for years. DNS on the shared network already
resolves service names.

**S2 — no healthchecks, no `depends_on: condition: service_healthy`.** php-fpm starts before
MariaDB is ready to accept connections. `links` orders startup, not readiness.

**S3 — `nginx:latest`** is an unpinned tag; `php:8.5-fpm` and `mariadb:10.11` carry no digest.
Builds are not reproducible.

**S4 — `expose: 9001` on the php service is wrong.** 9001 is the Xdebug *client* port on the
host; php-fpm listens on 9000 (`/usr/local/etc/php-fpm.d/docker.conf: listen = 9000`). The line
is a no-op that misleads readers.

**S5 — Xdebug is always loaded** via `zend_extension = xdebug`. `start_with_request = trigger`
removes most of the per-request cost but not the load cost, and there is no way to turn it off
without rebuilding the image.

**S6 — `container_name` plus `FASTCGI=${APP_NAME}-php85`** contradict the README's own advice to
run `docker compose -p okay_develop up -d`: the names are fixed, so project isolation breaks.
`fastcgi_pass php85:9000` over service DNS would work regardless of project name.

**S7 — the custom MariaDB entrypoint copies image internals.** `config/mysql/entrypoint.sh`
reimplements `docker_setup_env`, `docker_init_database_dir`, `docker_temp_server_start` and
friends in order to get an `/always-initdb.d` hook the official image does not provide. It works
today. Any upstream change to those internals breaks startup with no warning.

### Hygiene

**H1 — Dockerfile layer discipline.** `apt-get update` and `apt-get install` sit in separate
`RUN` layers (the classic stale-cache bug), no `--no-install-recommends`, no
`rm -rf /var/lib/apt/lists/*`, eight `RUN` instructions where two suffice, and no
`.dockerignore`.

**H2 — error reporting is backwards for a dev box.**
`error_reporting = E_ALL & ~E_NOTICE & ~E_STRICT & ~E_DEPRECATED` with `display_errors = Off`.
On PHP 8.4/8.5 the deprecation notices are exactly what a developer needs to see.

**H3 — nginx logs into the repository** (`/var/www/html/dev/logs/`), so `docker compose logs`
shows nothing for the web server.

**H4 — smaller items.** `MYSQL_USER: mysql` is hardcoded and a poor name; `restart:` is set only
on mariadb; `dev/.htaccess` is an Apache leftover that nginx already covers with a `dev/` 404
rule; no `TZ`; the README documents `TEST_INTERNAL_EMAIL` as the mail-testing story, which still
opens a real SMTP connection.

## Decisions taken

| Question | Decision |
| --- | --- |
| Existing 339 MB dev database | **Discard.** Fresh named volume initialised from `1DB_changes/okay_clean.sql`. |
| Prod layout | **base + override + prod.** `docker-compose.yml` is shared, `docker-compose.override.yml` is dev and auto-loads, `docker-compose.prod.yml` is opt-in via `-f`. |
| Extra dev services | **Mailpit only.** No Adminer. |
| Custom MariaDB entrypoint | **Replace with a one-shot `db-init` service.** The stock entrypoint stays untouched. |

## Design

### 1. File layout

```
dev/
├── docker-compose.yml            # base, shared by dev and prod
├── docker-compose.override.yml   # dev, auto-loaded by Compose
├── docker-compose.prod.yml       # prod, requires an explicit -f
├── .env-example
├── .dockerignore
├── docker/
│   └── Dockerfile                # multi-stage: base → dev / prod / nginx-prod
└── config/
    ├── php/
    │   ├── custom.d/okay.ini     # shared settings
    │   ├── custom.d/dev.ini      # display_errors, full E_ALL, msmtp sendmail_path
    │   ├── custom.d/xdebug.ini
    │   └── prod/opcache.ini      # COPYed into the prod stage, not mounted
    ├── mysql/db-init.sh
    └── nginx/templates/okay.conf.template
```

The Dockerfile sits at `dev/docker/Dockerfile` rather than under `docker/php/`, because it now
builds the nginx prod image as well as the PHP ones.

Deleted: `docker/mysql/Dockerfile`, `docker/nginx/Dockerfile`, `config/mysql/entrypoint.sh`,
`config/mysql/startup.sh` (folded into `db-init.sh`), `config/php/php.ini`, and the generated
`config/nginx/okay.conf`.

`dev/.htaccess` (`deny from all`) is **kept**. The nginx config already returns 404 for `dev/`,
but the file costs nothing and is the only protection for anyone serving the tree with Apache.
Removing it would be a small security regression for no gain.

**`.gitignore` change required.** The repository root `.gitignore` currently lists
`dev/docker-compose.override.yml`. Since that file becomes the committed dev configuration, the
line must be removed. A new ignore entry `dev/docker-compose.local.yml` takes its place for
personal tweaks, attached with an explicit `-f`.

### 2. PHP configuration without shadowing (fixes C2)

```yaml
environment:
  PHP_INI_SCAN_DIR: /usr/local/etc/php/conf.d:/usr/local/etc/php/custom.d
volumes:
  - ./config/php/custom.d:/usr/local/etc/php/custom.d:ro
```

PHP scans both directories. The stock `conf.d/` is left intact, so every
`docker-php-ext-*.ini` loads normally and the manual `extension =` lines are deleted. A newly
installed extension now works without a second edit.

`PHP_INI_SCAN_DIR` is read by the PHP binary itself, so it applies to `php-fpm`, the `./ok` CLI
and PHPUnit alike.

### 3. Dockerfile

One multi-stage file, `dev/docker/Dockerfile`:

```dockerfile
FROM php:8.5-fpm AS base
COPY --from=mlocati/php-extension-installer:2 /usr/bin/install-php-extensions /usr/local/bin/
RUN install-php-extensions pdo_mysql mysqli gd zip xsl xmlwriter opcache
ARG APP_UID=1000
ARG APP_GID=1000
RUN groupmod -o -g "$APP_GID" www-data && usermod -o -u "$APP_UID" -g "$APP_GID" www-data
WORKDIR /var/www/html

FROM base AS dev            # + xdebug, composer, msmtp
FROM base AS prod           # + application code, composer install --no-dev -o, USER www-data
FROM nginx:1.29-alpine AS nginx-prod   # COPY --from=prod for static assets
```

`mlocati/php-extension-installer` replaces the hand-rolled `apt-get` blocks: it resolves the
system libraries each extension needs and cleans up after itself, which collapses eight `RUN`
layers to two and removes the stale-cache bug (H1).

The build args are named `APP_UID`/`APP_GID`, **not** `UID`/`GID` — `UID` is a readonly shell
variable in bash and zsh and never reaches Compose's environment.

The service keeps the name `php85`. Renaming it to `php` would be cleaner long-term but would
invalidate `docker compose exec php85 …` in `CLAUDE.md` and in the team's muscle memory; the
churn is not worth it in this change. `container_name` stays in the dev override for the same
reason, and is absent from the prod file.

### 4. Database (fixes C1, S7)

```yaml
mariadb:
  image: mariadb:10.11
  volumes:
    - db_data:/var/lib/mysql
    - ../1DB_changes/okay_clean.sql:/docker-entrypoint-initdb.d/init.sql:ro
  healthcheck:
    test: ["CMD", "healthcheck.sh", "--connect", "--innodb_initialized"]
volumes:
  db_data:
```

Stock entrypoint, no `usermod`, no custom Dockerfile. `docker compose down -v` now genuinely
resets the database.

`db-init` is a one-shot service on the same image. It waits for `mariadb` to report healthy,
runs `config/mysql/db-init.sh`, and exits 0. The script:

1. Resets the `admin` manager to password `1234`, creating the row if absent — identical SQL to
   today's `startup.sh`.
2. Points `ok_settings.smtp_server` at `mailpit` and `smtp_port` at `1025`, so the SMTP path in
   `Okay/Core/Notify.php` cannot reach a real mail server from a developer's machine. Skipped
   when `DB_INIT_SMTP=0`.

Step 2 writes to the live dev database only. `1DB_changes/okay_clean.sql` is never modified.

### 5. Mailpit — both transports

`Okay/Core/Notify.php` sends mail two ways, and both need intercepting:

- `mail()` at line 183 → the dev image installs `msmtp` and sets
  `sendmail_path = /usr/bin/msmtp --host=mailpit --port=1025 -t`.
- `SMTP()` at line 81 → host and port come from database settings, handled by `db-init` above.

Mailpit runs with `MP_SMTP_AUTH_ACCEPT_ANY=1` and `MP_SMTP_AUTH_ALLOW_INSECURE=1`, because
`Notify.php:92` unconditionally sets `SMTPAuth = true` and Mailpit would otherwise refuse the
`AUTH` command. Web UI on `${BIND_IP:-127.0.0.1}:${MAILPIT_PORT:-8025}`.

`TEST_INTERNAL_EMAIL` keeps working and stays documented; Mailpit is the stronger guarantee
because no mail leaves the host at all.

### 6. Remaining fixes

| Ref | Before | After |
| --- | --- | --- |
| C3 | `0.0.0.0:3306`, `0.0.0.0:80` | `${BIND_IP:-127.0.0.1}:${PORT}:…` |
| S1 | `links:` | removed; service DNS |
| S2 | none | `healthcheck` on every service + `depends_on: service_healthy` |
| S3 | `nginx:latest` | `nginx:1.29-alpine` |
| S4 | `expose: 9001` | removed |
| S5 | Xdebug always on | `XDEBUG_MODE=${XDEBUG_MODE:-off}`, switchable without a rebuild |
| S6 | `FASTCGI=${APP_NAME}-php85` | `FASTCGI=php85` |
| H2 | `~E_DEPRECATED` | dev: `E_ALL`, and `error_log` to stderr — see the correction below |
| H3 | logs into the repo | `/dev/stdout`, `/dev/stderr` |
| H4 | `MYSQL_USER: mysql` | `${MYSQL_USER:-okay}`; `TZ` added; `restart:` on every service |

Renaming the database user from `mysql` to `okay` applies to a **freshly initialised volume
only** — `MYSQL_USER` is read at first init and ignored afterwards. The existing data is being
discarded anyway, so this costs nothing, and it does not touch the application: checking
`config/config.local.php` shows the app connects as `db_user = "root"`. The `MYSQL_USER` account
is used only by the init script.

**H5, found while checking the above — the application connects to MariaDB as `root`.** That is
the shipped dev default and it is not worth changing in dev, where root is `root`/`root` by
design. The prod profile must not inherit it — see section 8, which covers `config.local.php`
end to end.

### 6a. Correction: `display_errors` is decided by the application, not by php.ini

The original H2 finding above was half wrong, and the review caught it. Reading the bootstrap:

```php
index.php:14           ini_set('display_errors', 'off');   // unconditional, before everything
index.php:43-46        if ($config->get('debug_mode') == true) {
                           ini_set('display_errors', 'on');
                           error_reporting(E_ALL);
                       }
backend/index.php:19   ini_set('display_errors', 'off');    // same pattern
backend/index.php:47-49
```

So for any web request OkayCMS overrides whatever php.ini said. `display_errors` in an ini file
changes nothing for the storefront or the admin panel; **`debug_mode` in
`config/config.local.php` is the real switch**, and `config/config.php:45` already ships
`debug_mode = false`, so production is safe by default with no ini work at all.

What the ini settings still govern, and why they are worth fixing anyway:

- errors raised **before** line 14 — parse errors, a failed `vendor/autoload.php`
- the `./ok` CLI and PHPUnit, which never run `index.php`
- `error_reporting`, which sets the baseline until line 45 raises it

So the dev ini keeps `error_reporting = E_ALL` (dropping the `~E_DEPRECATED` mask matters on PHP
8.4/8.5) and adds `error_log = /dev/stderr` so that logs land in `docker compose logs`. It no
longer claims to control `display_errors` for web requests, because it does not.

**Structural guarantee that dev settings cannot reach prod.** Rather than relying on "the prod
compose file just does not mount `custom.d`", the ini files move into the image stages:
`dev.ini` and `xdebug.ini` are `COPY`ed in the **dev stage only**, and `prod/*.ini` in the prod
stage only. A prod image therefore does not contain `dev.ini` at all — there is no mount to
forget and no override to get wrong.

New `.env` keys: `APP_UID`, `APP_GID`, `BIND_IP`, `XDEBUG_MODE`, `MYSQL_USER`, `MAILPIT_PORT`,
`TZ`, `DB_INIT_SMTP`.

### 7. Production profile

`docker-compose.prod.yml` overrides the base with:

- `php85` built at `target: prod` — application code baked into the image, no source bind mount,
  `composer install --no-dev --optimize-autoloader`, `USER www-data`.
- nginx built at `target: nginx-prod`, carrying the same static assets, so the two containers
  cannot drift.
- `XDEBUG_MODE=off` and no Xdebug in the image at all.
- opcache with `validate_timestamps=0`.
- MariaDB publishes no ports.
- `restart: unless-stopped` and a `max-size` logging cap on every service.

**Deliberately out of scope**, to be stated plainly in the README rather than half-built: TLS and
certificates, backups, and a secrets manager. The profile assumes a reverse proxy in front that
terminates HTTPS.

## 8. `config/config.local.php` — the file the prod profile must handle carefully

Production reads its database credentials from the same `config/config.local.php` as dev.
`Okay\Core\Config::initConfig()` parses `config/config.php` first, then overlays
`config.local.php` when it exists. Two consequences that the first draft of this design got
wrong:

### 8.1 The dev credentials would be baked into the production image

`config/config.local.php` is listed in `.gitignore`, which is why it was easy to overlook — but
**a Docker build context reads the filesystem, not git**. A prod stage doing `COPY . /var/www/html`
would pick up the developer's local file, complete with `db_user = "root"` and the dev password,
and bake it into an image that then gets pushed to a registry.

Mitigation, both halves required:

- `dev/.dockerignore` excludes `config/config.local.php`, plus `dev/.env`, `dev/mysql/`,
  `dev/logs/`, `.git/`, `vendor/`, `compiled/`, `cache/`.
- The prod compose file supplies the file at **runtime** as a read-only bind mount
  (`./config.local.prod.php:/var/www/html/config/config.local.php:ro`), never from the image.
  A `config.local.prod-example.php` is committed as the template; the real file is gitignored.

That runtime file is also where H5 is resolved: it sets `db_user` to the unprivileged
`${MYSQL_USER}` account rather than `root`, and `debug_mode = false` (which section 6a shows is
the actual control over error output).

### 8.2 `Config::salt` is derived from the config file's inode and mtime

```php
$s = stat($this->configFile);
$this->salt = md5(md5_file($this->configFile) . $s['dev'] . $s['ino'] . $s['uid'] . $s['mtime']);
```

The salt depends on the device id, inode number and mtime of `config/config.php`. It is consumed
by `Okay\Core\Security\AdminRecoveryToken` (as the signing key for admin password-recovery
tokens) and as the `uniqid` seed in `OrdersEntity`.

In a container these values are properties of the image layer, so:

- **Every image rebuild changes the salt**, invalidating any outstanding admin recovery token.
  Low impact — recovery is a rare, retryable operation — but it will look like a bug when it
  happens, so it belongs in the README.
- **Two replicas built or stored differently can disagree on the salt**, and a token issued by
  one would fail on another.

This is not something the compose files can fix; it is a property of the application. It is
recorded here as an explicit constraint: **the prod profile is single-node.** Anyone scaling it
horizontally must first mount `config/config.php` from shared storage so that `stat()` agrees
across replicas, or change how the salt is derived. Neither is in scope for this change, and
neither will be implied to be handled.

## Verification

Green output alone does not count; each item below is a thing to look at.

1. `docker compose down -v && docker compose up -d` from scratch — all services healthy.
2. The database initialises from `okay_clean.sql`; `ok_settings` shows `smtp_server = mailpit`.
3. `http://okaycms.loc/admin` accepts `admin` / `1234` — checked in a browser, not by curl status
   code.
4. `docker compose exec php85 php vendor/bin/phpunit` passes.
5. `docker compose exec php85 php -m` lists every extension `composer.json` requires, with
   `custom.d` no longer masking `conf.d`.
6. A test email from the admin panel appears in the Mailpit UI.
7. `XDEBUG_MODE=debug docker compose up -d` makes a PhpStorm breakpoint fire; `off` unloads it.
8. `docker compose port mariadb 3306` reports a loopback bind, not `0.0.0.0`.
9. The prod profile **builds** (`docker compose -f docker-compose.yml -f docker-compose.prod.yml
   build`). It is not deployed anywhere, so "it runs in production" will not be claimed.
10. `docker run --rm <prod-image> cat /var/www/html/config/config.local.php` must fail with "No
    such file" — proof that `.dockerignore` kept the dev credentials out of the image (8.1).
    This one is a genuine test, not a formality: it is the check that would have caught the bug.
11. `docker compose exec php85 php -i | grep error_log` shows `/dev/stderr`, and a deliberate
    warning appears in `docker compose logs php85`.

## Risks

**`docker compose down -v` becomes destructive.** Today the database files survive it. After this
change the volume is removed and the database is gone. This is the intended behaviour — it is
what makes a clean reset possible — but it inverts a habit. The README must say so explicitly.

**`mlocati/php-extension-installer` is a third-party image.** It is the de facto standard for
PHP Docker images and is pinned to a major tag, but it is a new external dependency in the build.

**PHP 8.5 and Xdebug.** The current Dockerfile already carries a comment about commenting out the
Xdebug lines if no 8.5-compatible release exists. Moving to `install-php-extensions` does not
remove that risk; it must be verified during implementation, and the dev stage must fail loudly
rather than silently skip Xdebug.
