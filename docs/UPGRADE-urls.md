# Оновлення: url сутностей зводяться в нижній регістр

Стосується магазинів, які оновлюються на версію з нормалізацією url в адмінці.
Дія потрібна **до** викатки, і лише якщо перевірка нижче щось знайде.

## Що змінилось

Сім реквестів адмінки — товари, категорії, статті, категорії блога, бренди,
сторінки, автори — зводять `url` у нижній регістр при **будь-якому** збереженні,
не лише на створенні. Автогенерація url із назви й CSV-імпорт робили це й
раніше, через `Translit::translit()`.

Причина: MySQL порівнює url у `_ci`, тобто `Item-1` і `item-1` для бази це один
рядок, а для PHP — два. На цьому розходженні `ok_router_cache` набирав
`1062 Duplicate entry`, а перевірки унікальності в адмінці бачили різні
значення там, де база бачить однакові.

## Перевірка перед оновленням

```sql
SELECT 'products',        COUNT(*) FROM ok_products        WHERE BINARY url <> BINARY LOWER(url)
UNION ALL SELECT 'categories',      COUNT(*) FROM ok_categories      WHERE BINARY url <> BINARY LOWER(url)
UNION ALL SELECT 'pages',           COUNT(*) FROM ok_pages           WHERE BINARY url <> BINARY LOWER(url)
UNION ALL SELECT 'brands',          COUNT(*) FROM ok_brands          WHERE BINARY url <> BINARY LOWER(url)
UNION ALL SELECT 'blog',            COUNT(*) FROM ok_blog            WHERE BINARY url <> BINARY LOWER(url)
UNION ALL SELECT 'blog_categories', COUNT(*) FROM ok_blog_categories WHERE BINARY url <> BINARY LOWER(url)
UNION ALL SELECT 'authors',         COUNT(*) FROM ok_authors         WHERE BINARY url <> BINARY LOWER(url)
UNION ALL SELECT 'router_cache',    COUNT(*) FROM ok_router_cache    WHERE BINARY url <> BINARY LOWER(url);
```

**Усюди нулі — робити нічого не треба.** Оновлюйтесь і читайте далі лише з
цікавості: жоден зі сценаріїв нижче спрацювати не може.

## Якщо десь не нуль

Такі рядки варто вирівняти **разово, до викатки**. Ось що станеться, якщо цього
не зробити.

**Адреса зміниться сама.** Поле `url` у картці наявної сутності `readonly`, але
readonly-поле браузер усе одно надсилає. Тобто перше ж збереження картки — хай
навіть заради одного мета-тега — перепише url у нижній регістр. Стара адреса
далі працює: пошук за url скрізь нечутливий до регістру — товари, сторінки,
бренди й автори резолвляться SQL-ом у `_ci`, категорії та категорії блога —
згортанням у PHP. Але канонічною стане нова, а 301 зі старої ніхто не створює,
тож для пошукових систем це переїзд без попередження.

Заразом `CategoryAdmin` побачить зміну url і викличе `deleteProductsCache()` —
кеш маршрутів товарів злетить увесь. На каталозі в кілька тисяч товарів його
відбудова займає хвилини, і весь цей час `/sitemap.xml` може віддавати 504.
Вітрина при цьому працює, просто повільніше.

**Дві сутності, що відрізняються лише регістром, склеяться в одну.** Якщо в базі
лежать і `Katalog`, і `katalog`, то після цієї версії пошук за будь-яким із них
поверне перший знайдений, а другу картку адмінка перестане зберігати з помилкою
`url_exists`. UNIQUE на таблиці немає, тож такий стан у базі можливий — і саме
його знаходить перевірка з кроку 2 нижче.

## Порядок вирівнювання

1. Зробити дамп.
2. Перевірити, чи згортання не склеює дві різні сутності в одну — і саме ті
   групи, яких торкнеться `UPDATE`:

   ```sql
   SELECT LOWER(url), COUNT(*) c FROM ok_categories
     GROUP BY LOWER(url) HAVING c > 1 AND SUM(BINARY url <> BINARY LOWER(url)) > 0;
   ```

   Те саме для решти шести таблиць. Умова з `SUM(...)` не випадкова: без неї
   у вибірку потрапляють і давні точні дублікати, до яких це вирівнювання
   стосунку не має, і оператор іде перейменовувати живі адреси даремно. Якщо
   щось знайшлось — спершу розвести адреси вручну, бо `UPDATE` нижче зробить
   із них справжні дублікати.
3. Звести регістр у семи таблицях сутностей:

   ```sql
   UPDATE ok_products        SET url = LOWER(url) WHERE BINARY url <> BINARY LOWER(url);
   UPDATE ok_categories      SET url = LOWER(url) WHERE BINARY url <> BINARY LOWER(url);
   UPDATE ok_pages           SET url = LOWER(url) WHERE BINARY url <> BINARY LOWER(url);
   UPDATE ok_brands          SET url = LOWER(url) WHERE BINARY url <> BINARY LOWER(url);
   UPDATE ok_blog            SET url = LOWER(url) WHERE BINARY url <> BINARY LOWER(url);
   UPDATE ok_blog_categories SET url = LOWER(url) WHERE BINARY url <> BINARY LOWER(url);
   UPDATE ok_authors         SET url = LOWER(url) WHERE BINARY url <> BINARY LOWER(url);
   ```
4. `ok_router_cache` **не оновлювати, а очистити**:

   ```sql
   DELETE FROM ok_router_cache;
   ```

   `UPDATE` там може впертись у `UNIQUE url_type`. І скидати треба весь кеш, а
   не лише рядки зі змішаним регістром: `slug_url` товару містить url його
   категорії, тож після перейменування категорії закешований slug веде в
   нікуди. Це кеш, він відбудується сам — але не миттєво: на 7840 товарах
   повна відбудова близько трьох хвилин, і поки вона йде, `/sitemap.xml` може
   віддавати 504. Робити у вікно з малим трафіком і потім прогріти кількома
   запитами `/sitemap.xml`.
5. Повторити перевірку з початку документа — усюди нулі.
6. Викотити код.

## Що зі старими адресами

Товари, сторінки, бренди й автори за старим написанням відкриються й далі:
їх шукають SQL-запитом, а колонка в `_ci`. Категорії — теж, бо їхній пошук
тепер нечутливий до регістру. **Але шлях товару з категорією в старому
регістрі не відкриється**: патерн маршруту будується з url категорії в базі, а
роутер порівнює URI побайтово.

Канонічною скрізь стає нова адреса, редиректа ніхто не створює. Якщо змінені
адреси проіндексовані, 301 доведеться завести самостійно — і врахувати, що
модулі редиректів часто нормалізують вхідний шлях перед пошуком і відкидають
редирект, у якого джерело збігається з ціллю. Редирект «лише регістр» у такому
модулі не спрацює; потрібне правило на рівні nginx.
