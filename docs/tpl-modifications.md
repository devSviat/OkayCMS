# Модифікація `.tpl` з модуля

Модуль не редагує чужі шаблони — він описує зміни декларативно, а система застосовує їх до
вмісту шаблону перед компіляцією. Оригінальний файл лишається недоторканим; змінений варіант
існує лише як скомпільований PHP у `compiled/<тема>/` (вітрина) чи `backend/design/compiled/`
(адмінка).

Код живе в `Okay/Core/TplMod/`. Точка входу — `pre`-фільтр Smarty, який `Design` вішає при
створенні.

## Коли що використовувати

| Задача | Механізм |
| ------ | -------- |
| Вставити розмітку у відведене місце | блок дизайну ([modules/frontend.md](modules/frontend.md#блоки-дизайну)) |
| Змінити чужу розмітку там, де блоку немає | **модифікація `.tpl`** |
| Змінити дані, а не розмітку | розширення ([modules/extenders.md](modules/extenders.md)) |

Блок дизайну — надійніший: він не залежить від структури чужого шаблону. Модифікація — засіб
на випадок, коли блоку немає.

## Дерево вузлів

Шаблон розбирається в дерево. Вузлом може бути і HTML-елемент, і Smarty-конструкція.

Дочірні вузли можуть мати лише блокові теги; самозакривні (`<img>`, `<br>`, `<input>` …) і
текстові — ні. Зі Smarty-конструкцій дітей мають тільки `{foreach}`, `{function}` і `{if}`
(`{foreachelse}` і `{else}` стають текстовими дітьми). Решта Smarty-тегів — текстові вузли.

Іменем вузла є його відкривальний елемент — або весь елемент, якщо це самозакривний тег чи
текст.

```smarty
<div class="some-class">
    {foreach $arr as $item}
        {$item|escape}
    {/foreach}
</div>
```

Три вузли: блоковий `<div class="some-class">`, його дитина `{foreach $arr as $item}` і її
дитина `{$item|escape}`.

## Опис змін

Усе описується в блоці `modifications` файла `Init/module.json`
([modules/structure.md](modules/structure.md#modulejson)):

```json
{
  "modifications": {
    "front": [
      {
        "file": "order.tpl",
        "changes": [
          { "find": "{if $delivery}", "appendAfter": "order_delivery_info.tpl" }
        ]
      }
    ],
    "backend": []
  }
}
```

`file` зіставляється **із кінцем шляху** шаблону, тож достатньо імені файлу.

### Пошук вузла

У кожній зміні **обов'язковий** `find` або `like` — інакше система кидає
`Change must have "find" or "like" param in module "…"`.

| Ключ | Як шукає |
| ---- | -------- |
| `find` | входження підрядка в елемент вузла |
| `like` | регулярний вираз |
| `parent` | піднятись до батька знайденого вузла |
| `closestFind` | підніматись угору, доки елемент предка не міститиме підрядок |
| `closestLike` | те саме за регулярним виразом |
| `childrenFind` | спуститись до першої дитини, що містить підрядок |
| `childrenLike` | те саме за регулярним виразом |

`parent` перевіряється на **наявність ключа**, а не на значення — `"parent": ""` вмикає його.
Так само `remove`.

Якщо `childrenFind`/`childrenLike` нічого не знайшли, **зміна пропускається цілком**, мовчки.

### Операції

Усі виконуються в цьому порядку, і **в одній зміні їх може бути кілька**:

| Ключ | Дія |
| ---- | --- |
| `append` | додати в кінець вмісту вузла |
| `appendBefore` | вставити перед вузлом |
| `prepend` | додати на початок вмісту вузла |
| `appendAfter` | вставити після вузла |
| `html`, `text` | замінити вміст вузла |
| `replace` | замінити сам елемент вузла |
| `remove` | видалити вузол |
| `comment` | підпис для налагоджувальних коментарів; типово `Vendor/Module` |

**Значенням операції може бути ім'я файлу.** Якщо значення збігається з наявним шаблоном,
підставляється його вміст. Пошук для вітрини: спершу
`design/<тема>/modules/<Vendor>/<Module>/html/`, потім `Okay/Modules/<Vendor>/<Module>/design/html/`;
для адмінки — тільки `Okay/Modules/<Vendor>/<Module>/Backend/design/html/`. Саме тому в
прикладі вище стоїть `"appendAfter": "order_delivery_info.tpl"`.

## Приклади

Додати щось до назви товару в `product_list.tpl`. Шукати вузол через `find` за
`{$product->name|escape}` не можна — під пошук підпадає ще й `alt` зображення. Два виходи:
через батька або регулярним виразом.

```json
{
  "file": "product_list.tpl",
  "changes": [
    {
      "find": "product_preview__name_link",
      "childrenFind": "{$product->name|escape}",
      "appendAfter": "Додали через батька"
    },
    {
      "like": "^\\s+?{\\$product->name\\|escape}",
      "appendAfter": "Знайшли регулярним виразом"
    }
  ]
}
```

## Порядок і вимкнення

Модифікації застосовуються у **зворотному** порядку модулів (за `ok_modules.position`).
Вимкнені модулі пропускаються.

Аварійний вимикач — директива `disable_tpl_mod` у конфізі (у `config/config.php` вона
закоментована).

## Налагодження

- Після зміни `modifications` **чистіть `compiled/`**.
- `smarty_force_compile = true` у `config/config.local.php` — компілювати шаблон на кожному
  запиті. На проді прибрати.
- `dev_mode = true` — навколо кожної застосованої зміни з'являються HTML-коментарі з підписом
  модуля. Без `dev_mode` коментарі не друкуються.

## Як перевірити, що анкери живі

`TplMod` шукає анкер серед **вузлів** розібраного шаблона, а не в тексті файлу. Тому `grep`
тут оманливий: рядок `<i>{$var}</i>` у файлі є, а в жодному окремому вузлі його немає —
парсер розкладає це на елемент `<i>` і текстовий вузол усередині.

Якщо анкер не збігся, вставки просто не буде: без винятку, без запису в лог, без поломки
сторінки. Модуль лишається увімкненим, його сторінка в адмінці відкривається, а блока на
вітрині немає. Помітити це можна лише очима й лише знаючи, що саме там мало бути. Тому
перевіряти треба явно:

```bash
php ok module:check-modifications          # увімкнені модулі, активна тема
php ok module:check-modifications --all -v
```

Команда розрізняє чотири причини:

| Що каже | Що сталось |
| ------- | ---------- |
| `NO ANCHOR` | `find`/`like` не збіглися в жодному вузлі |
| `CHAIN BROKEN` | анкер живий, але `closestFind`/`childrenFind` нікуди не привели |
| `FILE MISSING` | шаблона з таким іменем немає в темі |
| `MULTIPLE` | збіг у кількох вузлах — не помилка, але блок вставиться стільки ж разів |

Модулі в комплекті додатково закриті тестом `tests/TplMod/BundledModificationsTest.php`: він
звіряє їхні анкери з усіма темами поставки й шаблонами адмінки і бази не потребує. Це той
гейт, який ловить найчастіший регрес — правку `backend/design/html` після освіження адмінки.

Перевірка каже лише, що місце для вставки знайшлось. Чи блок правильно виглядає, чи валідна
вставлена розмітка і чи анкер збігся саме там, де задумано, — видно лише очима на сторінці.

## Пастки: як модифікація тихо ламає сторінку

Це найнебезпечніша частина механізму, і про неї треба знати до того, як писати першу зміну.

`TplMod` **друкує файл назад із дерева вузлів**. Тобто шаблон, який хтось модифікує, повністю
переписується з того, що вдалося розібрати. Якщо парсер чогось не з'їв, воно просто зникає:
розмітка обривається посеред сторінки, у лог не потрапляє нічого, HTTP-статус лишається 200.

Три відомі пастки:

1. **`<` будь-де, крім відкривального `{if}`.** Символ `<` у тексті (наприклад, `a < b`)
   обриває розбір, і решта файлу зникає.
2. **Тег, чиє ім'я є Smarty-змінною.** Ім'я тега має відповідати `[a-z0-9]+`, тож `<{$tag}>`
   не розпізнається.
3. **HTML-тег, відкритий в одній гілці `{if}` і закритий після `{/if}`.** Дерево не
   балансується, і розбір не завершується як слід.

Ще дві дрібниці того ж роду: `like` обгортається в делімітери `~`, тож `~` усередині виразу
ламає вираз; `<script>` без закривального тега кидає помилку.

За тим, щоб шаблони тем і адмінки лишались придатними для цього обходу, стежить
`tests/TplMod/ThemeTemplatesTplModTest.php` — він проганяє кожен `.tpl` через розбір і
друк і вимагає, щоб змінились лише пробіли. Якщо ви додаєте до теми розмітку з `<` у тексті,
цей тест впаде — і це саме те, чого від нього хочуть.
