# Життєвий цикл модуля

`Init/Init.php` успадковує `Okay\Core\Modules\AbstractInit` і зобов'язаний оголосити два
методи: `install()` і `init()`. Різниця між ними — коли вони виконуються, і вона визначає, що
можна писати в кожному.

| Метод | Коли | Для чого |
| ----- | ---- | -------- |
| `install()` | один раз, під час встановлення | створення таблиць, `setBackendMainController()`, `setModuleType()` |
| `init()` | **на кожному запиті** | реєстрація контролерів, розширень, полів, блоків, пунктів меню, задач планувальника |
| `update_x_y_z()` | під час оновлення версії (і під час встановлення) | міграції між версіями |

Найчастіша помилка — важка робота в `init()`. Він виконується на кожному запиті кожного
відвідувача, для кожного увімкненого модуля.

## Встановлення

Єдина точка входу — кнопка «Встановити» в розділі модулів адмінки. Порядок:

1. Перевірка, що модуль ще не встановлений. Повторне встановлення кидає
   `Module name "Vendor/Module" is already exists`.
2. У `ok_modules` додається рядок: `vendor`, `module_name`, `enabled = 1` і `version` із
   `module.json`.
3. Створюється об'єкт `Init` і викликається `install()`.
4. **Виконуються всі `update_x_y_z()` від `1.0.0` до версії з маніфеста** — на свіжому
   об'єкті `Init`.

Пункт 4 — те, на чому спотикаються. Модуль версії `1.2.0` на чистій інсталяції отримає і
`install()`, і `update_1_1_0()`, і `update_1_2_0()`. Тому update-метод має або бути безпечним
на порожній схемі, або дублювати те, що `install()` уже зробив, ідемпотентно.

## Оновлення

Кнопка оновлення в списку модулів. Порядок:

1. З `ok_modules` береться встановлена версія, з `module.json` — цільова.
2. Виконуються `update_x_y_z()` у діапазоні **(встановлена, цільова]** — нижня межа
   виключна, верхня включна, у порядку зростання версій.
3. `ok_modules.version` переписується версією з маніфеста.

**Окремий випадок форку:** якщо `ok_modules.version` порожня (NULL), стан модуля невідомий і
мігрувати нема від чого. У цьому разі жоден update-метод не виконується — записується лише
версія з маніфеста, щоб зникла фантомна кнопка оновлення. Це свідоме рішення: update-методи
не зобов'язані бути ідемпотентними.

### Правила іменування

Метод має відповідати `update_<число>_<число>_<число>` і бути **публічним** — його викликають
ззовні об'єкта. Ім'я порівнюється регулярним виразом, прив'язаним лише до початку рядка, тож
`update_1_2_0_hotfix()` теж підхопиться і виконається як `1.2.0`.

```php
public function update_1_2_0()
{
    $this->migrateEntityField(
        NPWarehousesEntity::class,
        (new EntityField('updated_at'))->setTypeTimestamp()
    );

    // Дані вже наявних рядків правимо через ServiceLocator: DI в update-методах немає
    $SL = ServiceLocator::getInstance();
    $entityFactory = $SL->getService(EntityFactory::class);
    $deliveryTypesEntity = $entityFactory->get(NPDeliveryTypesEntity::class);

    $deliveryTypesEntity->add([
        'name' => 'Відділення',
        'warehouses_type_refs' => '841339c7-…',
    ]);
}
```

Це `Okay/Modules/OkayCMS/NovaposhtaCost/Init/Init.php` — єдиний модуль у репозиторії з
реальними update-методами.

**У `install()` і `update_x_y_z()` немає ін'єкції залежностей.** Сервіси беруться через
`ServiceLocator::getInstance()`.

## Модулі, що постачаються з системою

Дамп `1DB_changes/okay_clean.sql` містить таблицю `ok_modules` **разом із рядками вбудованих
модулів** — із заповненими `type`, `backend_main_controller` і `version`. Після
`./ok database:deploy` вони вже «встановлені», і їхній `install()` не виконається.

Наслідок: зміну схеми вбудованого модуля треба вносити **і в дамп, і в `update_x_y_z()`** —
інакше вона застосується або лише на нових інсталяціях, або лише на наявних.

`./ok database:deploy` не має жодного стосунку до механізму модулів: він просто заливає SQL-дамп.

## Що відбувається на кожному запиті

Вітрина піднімає **увімкнені** модулі, адмінка — **усі**, щоб вимкнені було видно в списку.

Для кожного модуля по черзі:

1. **Ліцензійна перевірка.** Модуль, що її не пройшов, пропускається цілком.
2. Якщо модуль вимкнений (і піднімаємо лише активні) — його Smarty-плагіни підміняються
   заглушками, що повертають порожній рядок, і на цьому все. Плагін вимкненого модуля не
   ламає шаблон, а мовчки нічого не друкує.
3. `config/config.php` модуля дописується в конфіг.
4. Читається `module.json`.
5. **Маршрути.** Якщо модуль неактивний, кожен маршрут позначається як мок і не реєструється.
6. `Init/parameters.php` → у контейнер.
7. `Init/services.php` → у контейнер.
8. `Init/SmartyPlugins.php` → у контейнер, плагіни збираються для подальшої реєстрації.
9. Маршрути прив'язуються до роутера.
10. Створюється об'єкт `Init`, викликається **`init()`**, зібрані контролери адмінки
    перетворюються на `Vendor.Module.Controller`.

Звідси два практичні висновки:

- сервіси й параметри модуля доступні всередині `init()`, бо реєструються раніше;
- в адмінці `init()` **вимкненого** модуля теж виконається — його маршрути при цьому не
  працюють, але побічні ефекти в `init()` відбудуться.

Порядок модулів — за `ok_modules.position`. Модифікації `.tpl` при цьому застосовуються у
**зворотному** порядку.

## Порядок і конфлікти

- Два модулі не можуть зареєструвати маршрут з однаковим іменем — це кидає
  `Route name "…" already uses`, якщо тільки другий не оголосив `'overwrite' => true`.
- Два модулі не можуть додати однаковий пункт меню — `Menu item by path … already in use`.
- Один контролер адмінки не може отримати два дозволи — друга спроба кидає виняток.
